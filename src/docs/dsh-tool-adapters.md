# DSH 工具适配契约

本文件定义一类工具的共同契约：本仓注册、模型可直接调用、动作对应某个 DSH 原生工具的最小包装。它和 [extensions.md](./extensions.md)、[regressions.md](./regressions.md) 分工不同。`extensions.md` 记主动提供的扩展，`regressions.md` 记能被重跑检查的移植坑，本文件写这类工具必须守什么，以及 DSH 升级时怎么核查。

适用于本仓注册且替代 DSH 原生工具动作的工具；模型、角色等发现工具不属于包装。新增包装工具时沿用本契约。

## 不变量

包装工具与它对应的原生工具在这些方面保持一致。

- **调用形态**：调用方给什么就近似地传给原生服务，不引入原生工具没有的选择概念。
- **错误面**：输入错误走运行时的参数错误通道，不走普通失败。否则模型的重试与改写行为会变，同一个错误在两种工具上表现不同。
- **结果形状**：成功返回原生工具同样形状的结果，让调用方的读取逻辑可以互换。
- **缺失降级**：可选能力不可用时给出可执行的替代说法，不静默换成另一种行为。

## 允许的差异

包装的目的决定了它必然会和原生工具有差。差异要同时满足三条，缺一不可。

- 差异来自本仓要补的能力，不是为了写起来省事。
- 差异在模型面上写清，调用方不用读源码就能发现。
- 差异全量登记在差异清单里，每条写「原生行为 / 本仓行为 / 理由」，由契约测试核对。

差异清单放在测试里而不是本文。它是随实现变化的数据，本文只规定它必须存在、必须有这三列、必须被核对。

## 升级时核查什么

DSH 基线变化后，对每个包装工具核对下面五件事，任一变化都要在同一个提交里处理。

1. 原生工具的模型面参数集合。
2. 原生工具的配置字段集合，以及本仓装配行引用到的字段。
3. 原生工具依赖的服务调用与返回类型。
4. 原生工具的输入校验规则，特别是成对参数、默认值来源、字符串是否裁剪。
5. 已登记的差异是否仍然成立，理由是否仍然成立。

运行项目检查后，对照当前安装的原生工具逐项复核。测试覆盖以断言为准，未自动化的契约与差异理由由本次审查确认。

## 新增一个包装工具

先确认原生工具确实做不到，再包装。落地时补齐五样东西。

- 模型面 schema，与原生工具同名同义，只加本次必须加的部分。
- 错误面，输入错误走参数错误通道。
- 结果形状，与原生工具一致。
- 差异清单里的行，含理由。
- 契约测试里对该原生工具的断言。

装配行加进根 `cordis.patch.yml`，并核对该行的配置字段仍是原生包 `Config` 的字段。
