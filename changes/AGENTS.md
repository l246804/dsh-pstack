# changes 发布说明

本目录只放 `AGENTS.md`（本规则）和固定文件名 `RELEASE.md`（当前这次发布的说明）。`RELEASE.md` 由 agent 会话按版本间提交生成，发布时被 `vp run release` 消费并删除。

## 目标

`RELEASE.md` 是 GitHub Release 正文原文，读者是判断要不要升级的使用者和接手维护的人。它回答三件事：实现方式变了什么、为什么变、对使用者有什么影响，含是否破坏性和要不要迁移。末尾另附他人贡献鸣谢。

## 谁来写

每次发布前由用户在 agent 会话里触发。agent 读提交、查决策记录、归纳，逐条与用户确认后落盘，脚本不生成正文。

## 数据来源与归纳

- 提交：`git log --no-merges <上一 tag>..HEAD` 的标题与正文。上一 tag 用 `git describe --tags --abbrev=0 --match 'v[0-9]*'` 取，HEAD 就在该 tag 上说明没有新提交，停止。
- 改动：关键 `git diff`、`src/dsh.md`、`src/surface.json`、`native/upstream.lock.json`。
- 差异：之前怎样、现在怎样，从提交和 diff 归纳；新增能力没有「之前」，写新增了什么。
- 结果：使用者能感知什么、要不要迁移，从行为、测试、接口形状判断，但按工具粒度写，不抄具体字段。
- 原因：驱动它的真实约束或事件，比如上游 Cursor / Claude Code 的对应实现、DSH 平台哪里不支持、实践中踩过的坑，出自 `docs/decisions/` 决策记录和用户确认。
- 一条变更来自决策记录时，在原因里引用 `docs/decisions/<file>`。
- 贡献者：从 `<上一 tag>..HEAD` 的提交标题取 `#<PR>`，用 `gh pr list --state merged --base main --limit 100 --json number,author,mergedAt,title` 按 `mergedAt` 晚于上一 tag 的提交时间过滤，作者取 `author.login`；再用 `git log --no-merges --format='%an <%ae>' <上一 tag>..HEAD` 补直接推送的作者和 `Co-authored-by:` trailer。PR 作者以 gh 的账号为准，直接提交只写提交里的姓名，不反推账号；gh 不可用时回退到提交作者，并在确认时说明取不到 PR 账号。

## 逐条确认

先把每条归纳成一句话主干并归入小节，需要时补原因或影响，逐条与用户确认，用户改过才算定稿，不确认不落盘。只否定某条原因时只改原因，不重写已确认部分。用户口语回答原因时，agent 改写成简洁书面句再定稿。鸣谢名单同样逐条确认，缺 PR 号或账号时问用户，不猜。

## 内容规则

- 按变更性质分组：新增能力、行为变更、破坏性变更与迁移、修复、兼容基线、其他（内部）。有内容才出现该节，不写「无」。
- 同一提交包含多种独立变化时，拆成不同条目分别归入对应小节。
- 新增能力写新增什么、解决什么问题、怎么用。
- 行为变更写「之前怎样 → 现在怎样」。
- 修复写原问题 → 现在，原问题须是上一发布版本已存在、用户会遇到的；同一发布范围内新增功能自身的修正，并入该能力或「其他（内部）」，不作为修复。
- 兼容基线只在 DSH 范围或 pstack 版本变化时出现，写旧值 → 新值；DSH 范围变化要提示先升级 DSH。
- 破坏性只登记在「破坏性变更与迁移」。迁移只在需要用户手动处理时写，例如配置、设置或用户可见行为；工具调用层的接口变化由 agent 在真实调用时按新定义自动适配，不写迁移。没有破坏性时不设该节。
- 原因和影响是可选项，只在非显然或需要使用者动手时写。
- 精简优先：正文只留读者要动手或要感知的信息。一条写成一到两句主干，不写提交流水账，不堆内部文件名；工具、参数、返回结构这类接口细节按工具粒度描述，不逐项列参数改名、字段或返回形状，需要时指向工具定义；用法按步骤一句一句写，不展开背景。
- 纯内部重构、文档措辞、CI 微调，除非影响使用者或维护者操作，并入「其他（内部）」一行或省略。
- 随包发布、用户能直接调用的能力内容（技能、命令）算用户可见，不归「其他（内部）」；只有实现层重构才算内部。
- 概要 2 到 4 句，点出最关键的 1 到 2 条变化，说明是否需要先升级 DSH。
- 鸣谢只列发布者之外的真人：排除仓库 owner、当前 `gh` 账号、`author.is_bot` 为真者，以及仓库内的 agent 身份（`dsh-pstack`、`pstack-agent`）。每条写成 `- @<login>（#<PR>）`，没有 PR 的直接提交写 `- <姓名>`，取不到账号就不写账号。没有他人贡献时整节省略，不写「无」。鸣谢放在正文末尾，不参与变更分组。
- 不编造。拿不准的原因标「待确认」并问用户，不自己补。

## 文件与生命周期

- 固定文件名 `changes/RELEASE.md`。
- `vp run release` 先校验它存在且已提交、无未提交改动，缺失或不满足就报错退出，不进入 bumpp。
- bumpp 创建本次版本的 release commit 与 tag 后，`release.sh` 才删除 `RELEASE.md` 并提交；只有 bumpp 已推送该提交时才推送清理提交，本地演练保持本地。未创建本次 tag 时保留说明；tag 保留原文供 GitHub Release 读取。
- tag 工作流在发布 npm 包前检查说明存在且非空。
- 发布前如果工作区又有新提交，重新生成并复核 `RELEASE.md`。

## 落盘前自检

- 每条归入正确小节，空小节已删。
- 需要用户操作的破坏性变更都写了迁移；纯工具接口变化没写迁移。
- 原因有决策记录或用户确认的来源，没有编造、没有凑字。
- 接口细节停在工具粒度，没逐项列参数、字段或返回形状；用法只写步骤。
- 概要点出关键变化和是否要先升级 DSH，没有提交流水账。
- 鸣谢只含发布者之外的真人，每条有 PR 号或提交依据；没有他人贡献时整节已删。
