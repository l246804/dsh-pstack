# 检查项目文档漂移

将持续维护的项目文档与当前证据对照。以只读报告结束，或应用经批准的文档修复。技能修改文档，不修改文档所描述的行为。遵循目标项目的归属和生成规则，不预设固定仓库结构或工具链。

## 选择模式

- **Report：**`/docs-drift` 或 `/docs-drift report`。执行步骤 1–5，不写文件。
- **Fix：**`/docs-drift fix`。执行同样的检查，再执行步骤 6–7。调用 Fix 本身不构成写入批准。

接受可选的路径或 glob，用于增加或收窄候选集合，也接受可选排除项。请求的模式或范围有歧义时先询问。

在整个审计中使用以下工作记录：

- **DocumentCoverage：**路径、分类、可审计性、编辑途径、已检查 claim 数、发现数和未核验数。已检查数是 supported、contradicted 和 unverified 的总和。未核验数是其中的子集，不另行累加。
- **Claim：**稳定 ID、文档位置、一个可独立核验的陈述、类型、证据和结果。一句话包含多个独立事实时拆成多个 claim。导航和过渡文字无需建 claim。
- **Finding：**一个或多个 claim ID、当前原文、证据、建议的文档修改或证据需求，以及处置结果。

只统计实际追溯到证据或有明确证据边界的 claim。计划中的检查和尚未检查的文本不计入。

## 1. 发现维护中的文档

用户给出路径时从这些路径开始。否则使用实际存在的根入口文档和维护规则，包括链接到的语言版本。不要求存在 agent 文档、README 或其他常规入口。记录已声明指针的缺失目标，不创建替代文件。

读取项目维护规则，跟随将文档指定为 agent 必须阅读、更新或保持同步之对象的指针。使用项目真实的文档名称与位置。常规架构、术语或决策文档路径只是调查线索，不是必备条件。普通链接可以作为证据或接受链接检查，但不因此递归加入全文巡检。

用户显式指定的文档即使通常只作参考，也是本次审计目标。将显式路径、glob、收窄和排除应用于候选集合。“整个仓库”只扩大候选发现范围，不使仓库内每份文档都成为项目维护文档。读取管辖每份候选文档的规则。项目自有的文档维护规则本身也是 maintained 文档。

根据项目指针、管辖指令、归属及更新约定给每个候选文档分类：

- **maintained：**由本项目所有，并随项目实现或工作流迭代更新。执行全部检查。
- **reference：**为其他 claim 提供证据，不作为审计目标。它可以由项目维护，也可以来自外部。记录它不进入维护文档集合的原因。
- **excluded：**不在请求范围内，或被显式规则排除。
- **unresolved：**维护归属不明确。纳入前先询问，同时继续分类无关候选文档。

不按路径、目录名、文件类型或文档主题推断归属。项目指针要求维护的目标属于 maintained。另行判断它是否可直接编辑。对生成、vendored 或上游内容，遵循项目声明的来源和更新流程。外部或 vendored 文档不自动成为 reference。每个 reference 行写明它回答的证据问题。每个排除或未决行引用显式规则或决定。

检查 claim 前，使用项目可用的版本控制状态检查候选文档及证据来源。在 Git 项目中，记录 `HEAD`，并对这些路径运行只读 `git status`。其他项目记录没有这类基线。区分基线明确的可读文档与工作区改动使预期状态无法判断的文档。标明仅存在于当前工作区的证据。不得为获得基线而 stash、reset 或覆盖改动。

每个候选文档都有一行 DocumentCoverage、有来源依据的分类、可审计性，以及编辑途径或排除原因时，本步完成。

## 2. 盘点并核验每项 claim

阅读每份维护文档及管辖它的指令。先为每个章节或语义完整的段落块建立索引，记录行号范围。逐块记录发现的 claim，或该块没有可核验 claim 的原因。不得用抽样段落代替未阅读的章节。

为每项可独立核验的陈述建立带文档内稳定 ID 的 Claim。覆盖当前事实、要求、历史陈述、示例和摘要。先记录类型，再用当前实现取证。

按 claim 类型追溯到适当来源，例如代码、规格、配置、清单、真实目录、入口、绑定关系或相关测试。纯规格文档不需要用实现证据来确立其要求。记录确切来源和观察到的事实。文档中的路径只是调查线索，不是证据。现有只读项目检查能回答具体证据问题时加以使用，并记录命令与实际结果。

将每项 claim 标为 `supported`、`contradicted` 或 `unverified`。每个未核验 claim 必须记录已尝试的检查及观察到的失败或证据边界。没有来源依据的事实断言属于未核验，列入未核验清单，不因此单独产生 Finding。不得只因来源缺失就删除它。要求和历史陈述需要权威或历史证据，不要求与当前实现相符。当前行为 claim 与实现冲突时必须产生 Finding。只有引用具体的要求、规格、测试或用户要求，才能将其处置改为 needs-user-decision。保留互相冲突的权威来源。检查执行失败是审计限制，不能证明漂移或干净。工作区改动使预期状态不明时，相关 claim 标为未核验，无关 claim 仍可核验。

为每份文档记录哪些 claim 支撑步骤 3 的每项适用检查。只有块索引能证明不存在适用 claim 时才能记录 `not applicable`。不得抽查几条路径或示例就当作检查了全文。`limited` 仍须达到与 `checkable` 相同的 claim 盘点和检查覆盖。

每项 claim 都有证据支持的结果或明确边界，且每份维护文档的 claim 数与账本一致时，本步完成。

## 3. 执行全部检查

对每份维护文档中的适用 claim 执行每项检查。名称一致本身不能证明规则已解耦或正确。

**路径、目录树、命令、链接与指针。** 从引用所在文档解析仓库相对链接、路径与锚点。将目录树条目与真实文件或创建它们的代码对照。参数化路径须与构造函数及其调用方比较各段顺序和参数，字面存在性检查无法核验占位符。通过真实脚本、任务声明和参数解析器核对命令示例。只在只读且能回答具体 claim 时运行示例。条件允许时检查外链。网络或访问失败归为未核验，不判为死链。

**实现耦合。** 文档列出枚举、注册表、组、阶段或配置集合的成员时，定位权威定义。考虑文档用途和成员稳定性。通用流程规则重复会变化的内部成员时，即使名称当前一致也报告 **Implementation coupling**。建议改为适用性规则或指向该定义的引用。不要求同步改名，也不建议再复制一份清单。用户参考、支持矩阵、公开契约或固定记录格式可以有意枚举成员。将这些清单与消费者和权威定义核对，不强制改成通用规则。

**示例与临时清单。** 检查示例是否仍演示所述行为，以及状态、选择器、输入和预期结果是否仍然有效。把每个具体值追溯到当前实现。示例是否有用不影响其核验义务。永久规则列出等待一次性处理的事项，而事项或状态已过期时，报告 **Stale example**。管辖约定要求长期规则使用持久原则或检查清单时，将临时清单改为这种形式，不换成另一份当前名称清单。

**重复概念与权威。** 在同一文档内部及跨维护文档按概念分组 claim。比较重复定义、条件、例外和流程规则。提出合并前确定权威位置。重复规则必须链接权威位置，或有证据支持其独立存在。其他位置保留不增加义务的摘要、面向不同读者的细节和独有限定条件。没有明确权威的重复规则报告为 **Redundancy**，冲突规则报告为 **Contradiction**。

**环境、依赖与插件。** 根据目标项目的规格和清单，检查关于用户环境已具备或缺少可选能力的假设。根据声明来源和文档用途，核验具体包、插件、二进制和服务名称及安装建议。正常的安装指南可以写明自身依赖。文档禁止通用规则包含特定环境假设或名称时，将违规报告为 **Environment assumption**。只采用该项目显式声明的例外，并引用其元数据和授权依据。文档要求使用能力类别或适用性引用时，按此建议修改。没有管辖契约时，不把缺失的外部能力归类为实现缺陷。不将本检查变成名称黑名单。

**术语与语言版本。** 查找一个概念使用冲突名称、一个名称指代不兼容概念，以及定义偏离实际用法的情况。按项目指针和命名约定配对语言版本。维护中的语言版本必须配对。名称相似不使 reference 或 excluded 文档成为同步目标。配对二者的 claim，比较义务、例外、流程、路径、参数、数量、版本、示例、状态和摘要含义。任一侧变化后，必须有证据支持另一侧同步，才能判定该语言对干净。含义一致不要求逐字翻译。

**无依据扩写。** 查找无依据事实、假设、臆造理由、性能结论、测试覆盖和验收状态。将已证伪的扩写收缩为有证据支持的最小陈述。仅证据不足时将 claim 标为未核验，不作为删除候选。保留历史语境和明确的未来计划。

每项适用检查都有支撑它的 claim ID 或有块索引依据的不适用原因。每项矛盾 claim 或已被证伪的扩写都对应一个 Finding。刻意契约通过与具名消费者或测试核对来保留。由此发现的漂移记录为 Finding，不能把契约当作静默豁免。满足这些条件时本步完成。

## 4. 判定权威并分类发现

按问题类型确定权威：

- 用户明确要求决定预期行为。
- 当前项目规格与有约束力的约定决定其声明的限制。
- 可核验的实现证据决定当前行为的描述。
- 文档的历史语境决定过去事件的表述。

证据能够确定当前事实，且编辑只纠正描述、消除真正冗余或清理无依据扩写时，适合修复文档。

证据不足、检查未完成或工作区基线不明时使用 `unverified`。记录限制，不要求用户裁决。权威来源冲突或选择会改变要求时使用 `needs-user-decision`。

出现下列情况时停止处理可修复项并询问用户：

- 实现可能有误，而文档可能表达的是要求。
- 修复会改变功能、公开契约、验收标准或既定约束。
- 已引用的要求、规格、测试与实现支持互不兼容的答案。
- 修复需要修改非文档内容，或绕过目标项目的来源归属、生成或更新流程。

继续只读检查无关项。未决项不进入修复计划。每项 Finding 都归为 `repairable`、`needs-user-decision` 或 `unverified`，且每项可修复动作只修改文档时，本步完成。

## 5. 报告

先报告范围和以下候选覆盖表。包含每个候选文档，claim 数为零的文档也不例外：

```text
路径 | 分类 | 可审计性 | 编辑途径 | 已检查 claim 数 | 发现数 | 未核验数
<path> | maintained | checkable | direct | <count> | <count> | <count>
<path> | maintained | limited | <source or update procedure> | <count> | <count> | <count>
<path> | reference | evidence-only | - | - | - | -
<path> | excluded | <reason> | - | - | - | -
<path> | unresolved | <reason> | - | - | - | -
```

为每份维护文档报告归属指针、每项 claim 的 ID 和位置、证据来源及结果，以及各项检查的结果或限制。使用紧凑表格即可。列出每项未核验 claim 的已尝试检查和证据边界。维护文档的可审计性使用 `checkable` 或 `limited`。其他分类对应使用 `evidence-only`、`not-audited` 或 `unresolved`，并在该列或分类中写明原因。跨文档 finding 在其引用的每份文档上都计入发现数。去重 finding 总数与逐文档计数之和分开报告。覆盖表计数须与 claim 账本及 findings 勾稽一致。仍有未核验或未决项时，`No confirmed findings` 只是不完整结果，不是干净结果。

每项发现使用以下结构：

```text
[Implementation drift | Implementation coupling | Stale example | Environment assumption |
 Contradiction | Terminology | Link | Redundancy | Language drift | Unsupported elaboration] 标题
  位置：<文档>:<行号或章节>
  现状：<当前原文>
  证据：<代码、配置、目录、测试、命令与观察事实，或证据边界>
  建议：<文档纠正、删除、合并、来源引用或待补证据>
  处置：repairable | needs-user-decision | unverified
```

冗余或耦合发现须写明权威来源，以及文档应保留或引用什么。没有现存权威且规则一致时，可以在纯文档提案中指定一个。义务冲突时使用 needs-user-decision。有已核验反证的无依据扩写须说明删除还是收缩。否则请求补充证据，并保持处置为 unverified。不得把需要用户决定或未核验项藏在干净结论中。有未核验 claim 且没有已确认发现时，写 `No confirmed findings; audit incomplete`，不写 `No drift`。

Report 到此结束，不写文件，也不创建报告产物。没有覆盖表和逐文档证据摘要时，无发现结论视为未完成。

## 6. 批准并修复

Fix 先复核覆盖表，将未核验或未决项排除在修复计划外。按文件和发现分组展示拟修改内容。为每个受影响文件展示精确 unified diff，包括语言版本和全部删除边界。为每个 hunk 标注 finding ID。同步修改必须包含在预览中。单独标明因未决问题而排除的修改。不得为生成预览而创建或修改文件。

请求明确批准并等待。用户可以只批准完整 finding 组的一个子集。同一语言对或其他原子同步内容必须放在同组。严格应用获批 diff，保留无关内容与用户已有改动。编辑前立即在版本控制支持时比较当前基线与已记录基线，否则直接比较目标文本和证据。若已变化或无法比较，停止并展示新的 diff 等待批准。

只通过获批 hunk 修复权威来源并同步有意的摘要和语言版本。派生文档遵循项目的来源归属和生成流程。可直接编辑的来源改动必须纳入获批 diff。合并必须保留每项独有要求、约束、注意事项与证据指针。出现新的语义冲突时停止该项并请求新的决定。

每个获批修改都已严格应用，或明确保持未应用并说明原因，且没有未获批文件变化时，本步完成。

## 7. 核验并收尾

重新阅读每份修改过的文档。重新检查其全部 claim，而不只是修改行。确认获批发现已解决、路径和链接可解析、对应语言视图一致，且没有未批准的语义变化。

运行相关的现有项目检查并记录实际结果。报告修改文件、已解决发现、获批保留项、未决问题、未核验陈述与验证证据。没有获批或需要修改的内容时，明确说明没有文件变化。

每项获批修改都有验证证据或具体的剩余失败，且每项检查都有实际结果时，本步完成。
