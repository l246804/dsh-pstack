# 升级 DSH 基线

运行时换成新的 DSH 版本后，先判断它有没有动到本仓的声明面，再决定要不要动任何东西。本文只写顺序和判断点，不写具体版本号、字段值或工具名。那些以 `package.json`、`pnpm-workspace.yaml`、根 `cordis.patch.yml` 和各文档的实际内容为准。

## 触发

运行时版本高于当前 `engines.dsh` 时，做一次影响面评估。

升级本身不等于移动基线。下限是一句承诺，只在破坏性变更迫使我们放弃旧版本时移动。新运行时通常仍然满足旧下限，此时正确的结论往往是「什么都不用改」。

## 先评估影响面

评估不是每次都要走完整流程。新版可能只动了与本仓无关的东西，这时重写适配答案和证据只会制造无意义的 diff，还会让「改过」看起来像「变过」。

走查区间从 `engines.dsh` 的下限起，到新运行时止。读新版本随附的升级说明，按它自己的索引逐站走；站的名字是被离开的版本，走到新版本前一站为止。一次安装里这些站是齐的，所以跨过多少个版本都能一次走完，不需要为中间版本单独留记录。

两样判断一起做。

1. **机器判定。** `vp run ci`。类型对着已声明的版本编译，契约测试读已安装的包，形状有没有动它先说。
2. **人的判定。** 逐条看走查区间里的破坏面，判断它落在哪一层。

判定标准只有一个，有没有破坏面落在本仓的声明面上。声明面是四处：`src/`、根 `cordis.patch.yml`、适配答案覆盖的事实、包装工具的原生契约。

- **没有落在上面。轻路径。** 不改任何文件，不产生提交。评估的结论就是「本次升级对本仓无影响」。代价是下次评估会从同一个下限重走这段区间，读几份指南的事，比维护一个「已评估版本」的状态便宜。
- **落在上面。完整路径。** 走下面一节。

判不出影响面时按完整路径走。无法核实时写未核实，不用旧结论填空。

## 完整顺序

1. **改版本声明。** `engines.dsh` 移到新下限，`pnpm-workspace.yaml` 里 DSH 与 Cordis 相关 catalog、lockfile、两份 README 的要求行与徽标一起动。兼容表不在这里改，它只记已发布事实，新范围由发版脚本在发版时写入。

2. **审装配。** 根 `cordis.patch.yml` 是本仓的装配清单，DSH 的工具、preset 和插件接口一变，模型看到的工具面就跟着变，所以这一项必须逐行核，不能只看报错。
   - 每个被引用的插件与行 id 是否仍然存在。
   - 每行的 `config` 字段在本仓装配里仍然有对应，语义未变。
   - preset 组合是否仍成立，子代理 preset 需要的服务是否仍由当前组合提供。
   - 工具名、技能目录、`dsh.client.inject` 是否仍是当前名称。
   - 新增或退役的官方工具是否需要本仓声明或屏蔽。

3. **刷适配答案。** 逐个替换项对运行时求证，改 `native/` 与 `src/` 的答案，以及每个本地化版本。

4. **刷证据。** 每个替换项的可复查位置重新落一遍。位置会失效，用符号名而不是行号。

5. **复核缺口。** 新机制可能让某条缺口不再成立。改判是用户的决定，不自行改状态；判据见 `native/AGENTS.md`。

6. **重建生成树。** `vp run native:generate`，产物与 `native/dsh.md` 同波提交。

7. **核对工具契约。** 按 `src/docs/dsh-tool-adapters.md` 跑契约测试并复核差异清单。

8. **验证。** `vp run ci`、`pnpm peers check` 与 `vp run native:generate:check` 全绿。

9. **发版。** 兼容表新分组由发版流程写入，迁移说明由发版说明承载。

## 判断点

- 下限是承诺，catalog 是编译基准，两者可以不同步。轻路径两者都不动；完整路径同时动。只有我们要用新 API 时 catalog 才需要跟着走。
- catalog 是单一查找表，同一项同时喂 `peerDependencies` 和 `devDependencies`，所以按精确版本钉。改写成范围会让类型编译用的版本随之浮动；而声明了 `engines.dsh` 时准入由它单独决定，精确 peer 不构成准入限制。
- 一条改动记录的是事实还是答案，决定它归第 1 步还是第 3 步。能用命令查出来的是事实，要读运行时才能确认的是答案。
- 破坏面只影响可选插件时，仍要在装配审查里写结论，说明当前组合为何不受影响。
- 完整路径改了适配答案，旧快照就不再对应当前答案。重跑由用户按需触发，不进本文步骤；快照记录的运行身份本来就不同步于下限，两者不是一条轴。
- 版本声明与适配答案可以分成两个提交，各自能单独验证。装配审查的结论跟版本声明一起交。

## 完成标准

完整路径：`vp run ci`、`pnpm peers check`、`vp run native:generate:check` 全绿，`engines.dsh` 与新运行时一致，装配审查每一项都有结论。

轻路径：走查区间逐站看完，结论是判定无影响。不产生提交。
