# 升级 DSH 基线

运行时换成新的 DSH 版本后，本仓的声明、装配、适配答案、证据和缺口要一起跟上。本文只写顺序和判断点，不写具体版本号、字段值或工具名。那些以 `package.json`、`pnpm-workspace.yaml`、根 `cordis.patch.yml` 和各文档的实际内容为准。

## 触发

`dsh --version` 与 `package.json` 的 `engines.dsh` 不一致时。

## 顺序

1. **读升级指南。** 已安装 DSH 的 `docs/upgrade-guide/` 按「从旧版本到新版本之间每一站」列破坏面，站的名字是被离开的那个版本。只读与 `src/`、根 `cordis.patch.yml`、适配答案相关的那几节。

2. **改版本声明。** `engines.dsh`、`pnpm-workspace.yaml` 里 DSH 相关 catalog、lockfile、两份 README 的要求行与徽标。兼容表不在这里改，它只记已发布事实，新范围由发版脚本在发版时写入。

3. **审装配。** 根 `cordis.patch.yml` 是本仓的装配清单，DSH 的工具、preset 和插件接口一变，模型看到的工具面就跟着变，所以这一项必须逐行核，不能只看报错。
   - 每个被引用的插件与行 id 是否仍然存在。
   - 每行的 `config` 字段是否仍是该包 `Config` 声明的字段，语义是否未变。
   - preset 组合是否仍成立，子代理 preset 需要的服务是否仍由当前组合提供。
   - 工具名、技能目录、`dsh.client.inject` 是否仍是当前名称。
   - 新增或退役的官方工具是否需要本仓声明或屏蔽。

4. **刷适配答案。** 逐个替换项对运行时求证，改 `native/` 与 `src/` 的答案，以及每个本地化版本。

5. **刷证据。** 每个替换项的可复查位置重新落一遍。位置会失效，用符号名而不是行号。

6. **复核缺口。** 新机制可能让某条缺口不再成立。改判是用户的决定，不自行改状态；判据见 `native/AGENTS.md`。

7. **重建生成树。** `vp run native:generate`，产物与 `native/dsh.md` 同波提交。

8. **核对工具契约。** 按 `src/docs/dsh-tool-adapters.md` 跑契约测试并复核差异清单。

9. **验证。** `vp run ci` 与 `vp run native:generate:check` 全绿。

10. **发版。** 兼容表新分组由发版流程写入，迁移说明由发版说明承载。

## 判断点

- 一条改动记录的是事实还是答案，决定它归第 2 步还是第 4 步。能用命令查出来的是事实，要读运行时才能确认的是答案。
- 破坏面只影响可选插件时，仍要在装配审查里写结论，说明当前组合为何不受影响。
- 无法核实时写未核实，不用旧结论填空。
- 版本声明与适配答案可以分成两个提交，各自能单独验证。装配审查的结论跟版本声明一起交。

## 完成标准

`vp run ci` 绿，`engines.dsh` 与 `dsh --version` 一致，装配审查每一项都有结论，`vp run native:generate:check` 绿。
