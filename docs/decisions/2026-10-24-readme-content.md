# 决定：README 的必填内容与边界

Status: accepted
Date: 2026-10-24

## 背景

README 是用户第一次接触插件的地方。当前 README 只有 Agent Team 警告和状态说明，缺少版本、依赖、安装、范围和排障信息。设计文档面向实现者，不能代替 README。用户要求 README 覆盖插件简介、已支持的 DSH 版本、实现原理、必要依赖、Agent Team 兼容性、安装方式、logo 和额外扩展，并且不写具体实现或源码说明。

## 决定

README 必须包含以下章节。内容只描述用户可见的行为、契约和限制，不写文件布局、内部模块、源码片段、构建命令或内部接口。

1. **简介。** 说明这是 pstack 的 DSH 移植，包含技能、playbook、原则和角色化子代理工作流，以及它适合什么任务。
2. **已支持的 DSH 版本。** 给出明确版本表。当前设计基线是 `0.2.1-rc.3`，`0.2.x` 是目标兼容范围，`0.3.x` 及以上未验证。最终以发布包的 `engines.dsh` 为准。
3. **实现原理。** 参考上游 pstack 对 Claude Code 的适配方式，用概念说明：保留上游技能原文，生成独立的宿主资产，用一份宿主适配说明处理工具、路径、模型和不可用能力的差异。不展开内部模块或源码。
4. **必要依赖。** worktree 插件是必要依赖。插件在 worktree 未启用时自动启用它，已经启用时不会重复启用。README 还要说明 worktree 只隔离工作目录和分支，不提供 VM、网络、凭据或端口隔离。其他依赖写 DSH 版本、Node.js 和 Git。
5. **Agent Team 兼容性。** 保留 [Agent Team 共存禁令](2026-10-24-no-agent-team-coexistence.md) 中的警告原文，并说明需要同时使用时用两个独立 profile。
6. **安装方式。** 说明最终通过 npm 发布，给出 `dsh plugin --profile <profile> add dsh-pstack` 形式的安装命令，以及安装后按 DSH 提示启用 bundle 或重启会话。包名和命令以正式发布为准。
7. **插件 logo。** README 顶部展示 `icon.svg`，并提供可读的替代文本。
8. **额外扩展。** 如果存在上游 pstack 没有的技能，增加一节列出名称、用途和启用方式。当前没有额外技能，因此省略该节，不用空章节占位。

以下章节同时纳入必填内容，原因是用户在没有它们时无法完成安装后的第一步或无法判断问题边界。

- **快速开始。** 依次运行 `/setup-pstack`、`/poteto-mode`，需要时用 `/poteto-help`。
- **角色配置。** 说明 `~/.dsh/pstack-models.md` 由 `/setup-pstack` 生成，支持 `inherit-parent`，panel 角色是列表，一行删除后回落到父路由。
- **功能范围与已知限制。** 列出 55 个技能、23 个 playbook、24 个原则和两个子代理人格。明确 `make-bot-ui` 不在首版。明确 Cursor 专属能力没有等价物，包括 Automations、cloud agents、Custom Modes、`/loop` 和 Bugbot 配置。明确 `typescript-best-practices` 的 `paths` 自动触发不支持，需要显式调用。说明 worktree 不是 VM、schedule 不是事件订阅、多模型评审需要真实不同的 route。
- **更新与卸载。** 给出升级和移除命令，说明角色文件在用户目录，卸载插件不会自动处理它。
- **平台与运行要求。** Linux 和 macOS 是主要验证目标，Windows 的 shell 和脚本支持尚未验证。Node.js 要求 `>=22.19`，worktree 需要 Git。
- **安全与数据。** 说明代理会在 DSH 权限模型下读写文件、执行命令，子代理继承调用方的策略。提醒不要把密钥写进角色文件或 prompt。会话记录保存在 DSH 的会话存储中，pstack 不另建云端记录。
- **故障排查与支持。** 给出先检查 DSH 版本、worktree 插件和 Agent Team 冲突的顺序，以及提交 issue 时需要附带的版本、profile 和最小复现。
- **目录。** README 超过一屏时提供目录。
- **许可证与上游归属。** 本包 MIT，上游 pstack 版权归 Lauren Tan，MIT，链接 `LICENSE`。

worktree 依赖承诺取代设计文档 §3.3 中把 worktree 视为可选依赖的表述。实现必须提供可验证的条件挂载，不能在 README 里声明而代码不兑现。检测和去重机制在实现阶段选定并用真实 profile 验证，覆盖安装、启用、禁用和升级路径。

## 备选方案

- 只写安装和兼容性警告的最小 README。放弃，因为用户无法判断版本、依赖、能力和限制。
- 把设计文档当作 README。放弃，因为设计文档包含实现细节、源码位置和验收步骤，不适合作为用户入口。
- 在 README 里写完整架构和源码说明。放弃，用户明确要求不写具体实现方式，这些内容应留在设计文档。
- 暂时不写 worktree 自动启用，只写可选依赖。放弃，用户明确要求 README 写明自动启用且不重复启用。

## 后果

README 会更长，但用户可以在一个页面内完成安装、配置、首次任务和排障。设计文档继续承担实现细节，两边不重复。

worktree 自动启用成为产品承诺。实现必须验证未启用、已启用、禁用后重新启用和升级四种情况，不能在 README 写一套、代码做另一套。

额外扩展章节是条件章节。没有上游之外的技能时不出现。等新增技能时再补，并说明它不属于上游 pstack。

发布包名或 DSH 支持范围变化时，README 的版本表和安装命令要同步更新。
