# 决定：第三方技能按来源分目录 vendored，用内容哈希固定来源

Status: accepted
Date: 2026-10-27

## 背景

`assets/skills/` 只有一个来源：pin 在 submodule 里的 pstack 树，由 `build:assets` 从上游加 patch 生成，`sync-upstream --check` 逐字节比对。这套机制假设"每个技能都能从同一个上游重新生成"。

这个假设在两种情况下不成立。一是上游依赖的 Cursor 内置技能无授权可移植，需要一个外部替代（见 [内置技能依赖记录](2026-10-27-cursor-builtin-dependencies.md)）。二是维护者后续想补充自己写的技能或其他仓库的技能，它们不来自 pstack submodule，生成器也不该管它们。

把这类技能塞进 `assets/skills/` 会同时破坏两件事：`build:assets` 会把它们当成需要生成的文件，`sync-upstream --check` 会报"没有上游来源"。而且它们各自有独立的上游、独立的许可证、独立的更新节奏，混在一棵树里就无法按来源更新，也无法回答"这个文件是谁的、凭什么能再分发"。

## 决定

新增 `assets/skills-ext/`，按来源分目录：`assets/skills-ext/<来源>/<技能>/`。来源目录用仓库名，例如 `mattpocock-skills`。

**来源与固定信息记在 `scripts/skills-ext/sources.yml`**，每个来源一条：仓库 URL、许可证、版权行、固定的提交 SHA、每个技能的路径、文件清单、每文件的 SHA-256。清单放在 `assets/` 之外，因为 provider 把技能根下的每个条目都当成技能目录，清单放进去会让插件启动失败。

**vendored 文本不许本地改。** 改一个字符哈希就对不上，`check` 失败。这样"手里的文本等于上游某次提交"这件事永远是机器可验的。确实需要本地改动时，它必须是放在那份拷贝之外的独立文件，并让清单与检查认得这个例外；改那份拷贝本身等于让哈希失去意义，那时这个来源就不再可验，宁可放弃这个来源也不要那样改。

**同步分两步，不合并。** `pnpm run skills-ext:sync` 去拉固定提交的远端内容比对，只报告。`pnpm run skills-ext:pin` 重新记录哈希。上游改进一个技能是评审决定：看完差异、决定采纳，才改 `revision` 再 pin。没有人会因为跑了一次同步命令就悄悄改变了 shipped 文本。

**两棵树不许同名。** provider 合并两个索引，重名抛错让插件启动失败，而不是让其中一个悄悄盖掉另一个。使用者自己写的同名技能则按 rank 遮蔽（本包 600，项目级 100、200，用户级 400、500），这一点写在 README 与差异清单。

**校验分三家。** `sync-skills-ext.ts` 管内容哈希与文件清单，`checkSkillsExt` 管打包规则（来源已登记、许可证非空、提交号是 40 位 SHA、名字 kebab-case、不与 pstack 树撞名），`sync-upstream --check` 与 `checkAssetsHostCopy` 明确跳过这棵树——它不由 pstack 生成，它的文本属于它的作者，改它的措辞会破坏那个证明拷贝可信的哈希。

## 备选方案

- **把第三方技能也放进 `assets/skills/`，用 patch 机制生成。** 放弃：生成器读的是 pstack submodule，这些技能不在里面；放进去要么让生成器假装它们来自 pstack，要么在生成器里开一堆特例。而且同一个目录下混着"可重新生成"和"只能原样复制"两种文件，`--check` 的语义就没法说清。
- **用 git submodule 管每个第三方来源。** 放弃：一个来源只有一个技能时，submodule 的成本（嵌套仓库、clone 要 `--recurse`、CI 要初始化）高于收益。而且 sources.yml 已经能精确到文件和哈希，比 submodule 的"整个仓库一起动"更细。来源多到需要整仓跟踪时再考虑。
- **不记哈希，只记 revision 和文件清单。** 放弃：那样本地改动无从发现。实测把 vendored 文件加一行，`check` 会报 `content differs from the pin`；没有哈希这一步就静默漂移了。
- **`--check` 默认联网比对上游。** 放弃：`pnpm run check` 必须能离线通过，否则 CI 会因为网络失败而红。联网比对放在单独的 `skills-ext:sync`，由人显式跑。
- **同步时自动采纳上游变化。** 放弃：那等于把 shipped 文本的决定权交给上游的推送。上游可能删掉一段我们需要的话，或改掉一处我们依赖的措辞。报告与采纳必须分开。
- **每个技能目录放一个 `SOURCE.md` 说明来源。** 放弃：来源信息已经在 `sources.yml` 里，再放一份就是同一事实两处维护，而且那份文件会让"每个发货文件都有上游路径"这条规则需要开口子。读者要查来源看清单，要查为什么这样决定看本文。
- **把清单放进 `assets/skills-ext/`。** 放弃：provider 把该目录下每个条目都当技能目录，一个 yml 会让插件直接启动失败。这是实测过的，不是设计偏好。

## 后果

补充第三方技能现在有了一条与 pstack 分开的路：加目录、登记来源、pin 哈希，三步。来源与许可证对每个来源可见，一个来源更新不影响另一个。本地改动、未登记文件、上游已变，三种失效各自有检查。

代价有四条。第一，多了一套并行的机制：`sources.yml`、`sync-skills-ext.ts`、`checkSkillsExt`，与 pstack 那套并列，读者要学两条路。第二，vendored 文本不能就地处改，小改动也要走 patch，这是为了让哈希保持有意义而付出的摩擦。第三，`checkAssetsHostCopy` 对这棵树不适用，意味着一个 vendored 技能里若出现别的主机的安装指令，只能靠评审来源条目发现，静词检查看不见。第四，`skill-ext` 的内容不计入 `capabilities.ts` 的能力映射，它提供的功能在能力表上没有行。

重新考虑的条件：来源超过五个、或单个来源的技能超过十个时，`sources.yml` 会长到需要拆分，那时应按来源拆成多个文件。如果真出现"必须改 vendored 文本"的需求，那是一个新决定：要么承认这个来源不再可验并把它降级为普通移植，要么在清单之外另建一套与 `patches.ts` 同等强度的 anchor 与证据机制。不要用后者冒充前者。
