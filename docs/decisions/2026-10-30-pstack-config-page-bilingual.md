# 决定：插件配置页默认提供中英双语

Implemented-by: -

## 背景

插件配置页面向 DSH 的中英文用户。新增角色模型配置页时，中文文案曾存在英文残留；配置页属于产品界面，不能依赖用户自行翻译或浏览器翻译。后续在配置页增加功能时，如果只补英文，会再次产生同样的双语缺口。多个配置能力共用同一份字典时，键名冲突会让一个能力的文案覆盖另一个能力。

## 决定

所有插件配置页的可见文案必须通过按能力拆分的本地化字典提供，并同时维护完整的 `en` 与 `zh` 词典；新增配置页功能时必须在同一个改动中补齐两种语言。

每个插件配置能力使用独立的 locale 命名空间和词典；不同能力不得注册到同一个命名空间，也不得向其他能力的词典写键或复用同义键。DSH `common` 命名空间只作为共享基础层，能力词典只放该能力自己的文案。角色模型配置页使用 `pstackRoles`，推荐插件页使用 `pstackPlugins`。

测试必须校验命名空间注册、各能力 `en` / `zh` 键集合完整，以及跨能力键集合无交集；各配置页至少渲染一次中文与英文。`locale/en.json` 与 `locale/zh.json` 的插件元数据保持对应语言。

## 备选方案

- 只提供英文文案。不选：中文用户无法在配置页完成操作，违背产品双语目标。
- 依赖浏览器自动翻译。不选：无法保证术语一致，翻译质量和不支持翻译的 Electron/WebView 环境不可控。
- 一次性补齐 DSH 支持的八种语言。不选：当前项目只承诺中英双语，扩到八种会显著增加翻译维护成本；以后需要时再扩展。
- 所有配置页共用一个 `pstackRoles` 字典，用键前缀区分能力。不选：词典所有权仍跨能力混在一起，新增或修改能力时容易覆盖其他能力的文案和键名。

## 后果

配置页保持中英双语一致，每个能力维护自己的命名空间、两种语言词典和对应测试。代价是每个能力多一份命名空间注册；若将来增加第三语言，需要扩展各能力的字典与测试。
