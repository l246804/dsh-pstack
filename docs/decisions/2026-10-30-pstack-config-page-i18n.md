# 决定：插件配置页文案使用通用 locale 目录，不绑定固定语言对

Status: accepted
Date: 2026-10-30
Scope: src/client/**, tests/**, locale/**
Implemented-by: commit:fd9a251393df8538cfc4826a9d40f6a789711932
Review: 2027-04-30

## 背景

插件配置页面向 DSH 的多语言用户，配置页属于产品界面，不能依赖用户自行翻译或浏览器翻译。此前的做法按一对固定语言（`en` / `zh`）组织：每个能力维护这两个语种的词典，其中一个的键集合约束另一个，测试只比较这两种语言。这把“支持哪些语言”写死成一组基对，后续增加第三种语言时，新增词典缺少的键不会在类型层面报错，容易留下“看似已国际化、实际漏翻”的键；评审也无法从结构上判断覆盖是否完整。

## 决定

所有插件配置页的可见文案通过按能力拆分的 locale 目录提供。`src/client/i18n.ts` 维护支持语言清单 `SUPPORTED_LOCALES` 与通用词典类型 `LocaleCatalog<Key>`：每个能力的 `catalogs` 必须为清单里的每种语言给出与基准键集相同的完整词典。新增一种语言只在 `SUPPORTED_LOCALES` 加一项，再由类型缺失和测试失败强制每个能力补齐，不额外引入按语言分支的逻辑。

每个插件配置能力使用独立的 locale 命名空间与目录；不同能力不得注册到同一个命名空间，也不得向其他能力的词典写键或复用同义键。DSH `common` 命名空间只作为共享基础层，能力词典只放该能力自己的文案。角色模型配置页使用 `pstackRoles`，推荐插件页使用 `pstackPlugins`。

测试遍历 `SUPPORTED_LOCALES`，校验各语言键集合与基准字典一致且非空、跨能力键集合无交集，并按每种语言渲染每个配置页；不再把基对写死为 `en` 与 `zh`。DSH 的 typed `locale.register` 仍要求 `zh` / `en` 基准，因此 `SUPPORTED_LOCALES` 必含二者；这是宿主接口约束，不是本项目的语言上限。`locale/<语言>.json` 的插件元数据按文件名语言各自维护。

## 备选方案

- 只提供英文文案。不选：非英文用户无法在配置页完成操作，违背产品国际化目标。
- 依赖浏览器自动翻译。不选：无法保证术语一致，翻译质量和不支持翻译的 Electron/WebView 环境不可控。
- 继续只维护 `en` / `zh` 一对词典，需要时再逐个能力补语言。不选：正是本次要消除的“漏盖嫌疑”——新增语言时类型和测试不会提示缺失键。
- 把某一种语言设为键集合的唯一来源、其他语言都从它派生。不选：仍把一种语言设成特权基准，新增语言要改那份类型；通用做法应让基准只定义键集，所有语言按同一契约对称补齐。

## 后果

配置页的文案覆盖由结构保证：支持语言清单是唯一入口，缺少任一语言的任一键都会编译失败，测试按清单全量校验。代价是每种语言多一份完整词典；`SUPPORTED_LOCALES` 必须始终包含 DSH 要求的 `zh` / `en` 基准，增加第三种语言时各能力字典与 locale 元数据文件要同步补齐。
