# 决定：README 的篇幅与版本写法

Status: accepted
Date: 2026-10-24

## 背景

[2026-10-24-readme-content.md](2026-10-24-readme-content.md) 定下了 README 的必填章节。成稿后暴露五个问题。目录在十几节的篇幅里重复了标题。开头的项目状态会随实现推进过期。版本表预写 `0.2.x` 和 `0.3.x`，把未验证的兼容性写成了承诺。正文里向读者交代文档分工，使用者不需要这层信息。整体篇幅超过首次使用所需。

## 决定

1. **不设目录。** 章节标题承担导航，不把标题再抄一遍。
2. **不写项目状态。** README 只写可用的行为、契约和限制。实现与发布进度由发布说明承载。
3. **版本只写已验证的。** 支持章节列当前验证过的 DSH 版本，新版本验证后补充。不预写 `0.2.x`、`0.3.x` 这类兼容范围。
4. **正文按读者分层。** README 写给使用者，回答怎么装、怎么配、能做什么、哪里会失败。移植思路要讲清楚，文档分工不在正文交代。
5. **篇幅服务于首次使用。** 保留安装、配置、首次任务、边界和排障需要的信息。依赖与平台要求合并到一处。

本记录收窄旧记录中的目录、状态、版本预测和篇幅要求，其余条款继续有效。

## 备选方案

- 保留目录。放弃，篇幅不足以需要导航。
- 保留状态段落。放弃，实现每推进一步就要改一次，且与发布说明重复。
- 版本表写目标兼容范围。放弃，未验证的版本写进 README 就是承诺。
- 保留全部推荐章节和原有篇幅。放弃，平台要求与依赖重复，排障和安全可以更短。

## 后果

README 更短，首次使用路径更直。版本章节每次发版要改一行，这是有意的维护成本。

README 面向使用者，实现细节由设计文档承载。
