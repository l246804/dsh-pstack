# 决策：项目文档和发布产物使用可扩展语言集合

Status: accepted
Date: 2026-11-13
Scope: README.md, README.zh.md, docs/**, src/**, playground/**, scripts/release-compatibility.ts, bump.config.ts
Implemented-by: commit:e0bb1d6
Review: 2026-11-23

## 背景

项目文档把支持语言写成固定语言名称，等于把当前 locale 数量写成了架构常量。新增语言时，流程说明、发布规则和兼容表维护都要再次改写，文档也会和当前实现耦合。语言支持应是可扩展的 locale 集合，文档应描述本地化机制，而不是把当前语言数量写死。

## 决策

- 文档使用“本地化版本”“各语言版本”“locale 集合”等表述，不把固定语言数量或语言名称当作规则常量。
- 当前实际存在的语言文件是当前 locale 的实例，不作为未来语言数量的约束。
- 新增语言时只增加对应 locale 内容和注册项，不修改流程性规则。
- 发布兼容表同步适用于所有已注册的本地化 README，不写死为固定文件；实现可以暂时只提供当前 locale，但文档和接口不应固化数量。
- 具体 locale 列表由配置或发布元数据提供，流程文档只说明如何使用该集合。
- 历史决策记录可以保留当时的实现事实，但新规则不得再以固定语言结构作为设计前提。

## 不需要泛化的内容

- 具体文件名和路径是当前实现事实，保留具体名称，例如 `README.zh.md`、`src/dsh.zh.md`。
- 历史决策记录保留当时的语言表述和实现事实，不因本决策改写历史。
- 决策记录的文件命名和正文语言属于当前项目写作约定，保持具体，不抽象成“某种语言”。
- 能力 inventory 的 `description` 语言由当前数据来源和用户约定决定，保留实际语言说明，不为了国际化规则改成空泛描述。
- 单个文档指向某个实际本地化文件时，可以写清该语言或文件名；“本地化版本”只用于流程规则和不指向具体文件的地方。

## 替代方案

**继续把固定语言数量写进流程和发布规则。** 新增第三种语言时需要修改多处流程文档，容易遗漏，也让语言支持看起来只有两个；该方案被否决。

**在每篇文档中列出当前支持的所有语言。** 这会把文档和当前 locale 列表绑定，新增或删除语言时产生大量重复修改；该方案被否决。

**只改 README 的语言切换，不定义项目级规则。** 发布、兼容表和文档流程仍会反复假设固定语言集合；该方案被否决。

## 后果

- 文档描述本地化机制，不描述固定的语言数量。
- 当前 locale 仍可正常工作，但不再被写成唯一结构。
- 发布和文档流程新增语言时需要扩展 locale 数据，而不是重写规则。
