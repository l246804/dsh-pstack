# 决定：把与上游的差异整理成一份受检查的清单

Status: superseded
Superseded-by: [2026-10-27-upstream-text-plus-adapter.md](2026-10-27-upstream-text-plus-adapter.md) — 整条被取代：清单、生成能力表与差异检查已删除，差异改由 docs/harness/dsh.md 一处记录，覆盖度从随包正文反推。
Date: 2026-10-26

## 背景

这个仓库是 pstack 到 DSH 的移植。移植必然产生差异：宿主工具名不同、有些能力这里没有、有些能力这里反而是另外的形态。差异本身不是问题，**差异没有被记录**才是问题。

已经发生过两次，形状不同、后果相同。

第一次是能力被删掉。上游 24 个文件要求调用方按任务难度选推理档位，重写把这句话换成"档位只能来自角色文件"，并让四处文档互相印证。静态门全绿，因为禁词检查只问"不该出现的词出现了没有"，对"能力消失了"不敏感。

第二次是同一处修复后留下的措辞偏差。恢复成 `starting baseline`，其中 `baseline` 是本仓库自造的词，读着像下限，恰好否掉了该能力最主要的用途。再修成上游原话 `starting level` 之后，又发现旁边写着"本包不假设存在通用档位阶梯"，于是上游"升一档 / 降一档"的定量指令被删成"调高 / 调低"的定性描述。实际上 DSH 的适配器按从低到高报告档位列表，一档是可以定义的。

两次的共性：**改动是自洽的**。代码、工具描述、技能正文、角色文件示例四层同时改成了同一个错误说法，所以没有任何一层与另一层矛盾，也就没有东西报警。

盘点时还发现两类同源问题。一类是按当时的实现状态写死了"某工具还没随附"，工具落地后变成假话。另一类是写"某工具是官方提供的"，而它其实来自一个可选插件，目标 profile 并未挂载。两者都是**关于能力存在与否的断言，没有任何检查去核对**。

## 决定

新增 `docs/upstream-divergences.md`，作为与上游差异的唯一清单，并让它在 `check:assets` 里受检。

清单本身记四件事：

1. 每条能力差异的类别（`mapped` / `degraded` / `preserved` / `excluded` / `regression`）与理由。
2. 措辞改写对照表，把"功能对等但写法不同"与"功能不同"分开，避免下一次同步把两类误判。
3. 推理档位单独成节，写明语义、判定为 regression 的条件，以及这处出过两次偏差的过程。
4. 同步上游的固定步骤，其中最后一步是更新清单本身。

判定标准只有一条：**功能是否对等**。措辞不同不算差异，能力丢失算。

新增 `scripts/divergence-ledger.ts` 里的 `checkDivergenceLedger`，在 `check:assets` 中运行，断言三件事：文件存在；四个基本类别各有定义；清单引用的能力计数与 `scripts/capabilities.ts` 一致，且每个被排除的能力都在清单里点名。

这条检查是**正向**的。已有的禁词检查都问"某个词在不该出现的地方出现了吗"，那种形状对"能力被删掉"完全免疫，因为删除只会让违规文本消失。正向检查问"这个能力还在吗"，才能抓住删除。

## 备选方案

- **不写清单，靠 `scripts/patches.ts` 里每条 patch 的 `reason` 字段。** 放弃：`reason` 是逐条改动的理由，读者要看完 339 条才能拼出"与上游的差异全貌"，而同步上游时的第一个问题恰恰是"整体差异是什么"。逐条记录是局部视角，清单是全局视角，两者不能互相替代。
- **清单只写 `degraded` 与 `excluded`，不写 `mapped`。** 放弃：`mapped` 占了 17 条，其中至少三处（`resume`、档位控制、随包脚本）看起来像降级而实际对等。不点明这三处，下一次同步会把它们当成遗漏去"补齐"。
- **让检查断言清单的每一条都用词与代码一致。** 放弃：那需要自然语言理解，而检查脚本只能做字符串匹配。能做到的边界是"计数与点名"，再往前一步就会变成断言清单自己，也就是用一个会过期的规则去校验另一个会过期的规则。
- **把清单放进 `docs/decisions/`。** 放弃：`docs/decisions/` 回答"当时为什么这样选"，一条决定写完就不再改。清单回答"现在差异是什么"，每次同步都要更新。两者生命周期不同，放进同一目录会让"记录不改写"的规则被破坏。
- **把清单生成出来，像 `assets/docs/harness/dsh.md` 那样。** 放弃：能力映射表确实是生成的，但清单的主体是判断（哪些差异可接受、哪些措辞是刻意的），不是数据。生成器只能产出后半部分的表，前半部分仍得人写，混合来源比整份手写更难维护。
- **只在 `check:assets` 里断言清单存在，不比对计数。** 放弃：只断言存在的话，改了 `capabilities.ts` 而没更新清单仍然全绿，而这正是要防的那种静默过期。

## 后果

同步上游现在有了一份可直接读的对照物。差异分三类记着，检查保证清单不会在代码变动后继续描述上一棵树。能力被删这类改动有了一个正向的抓手。

代价有三条。第一，清单是手写的，`checkDivergenceLedger` 只能核对计数和点名，核对不了"这条描述是否仍然准确"。那部分靠同步时的第 3 步人工判断，没有门守着。第二，新增了 192 行文档和 100 行检查，维护面变大。第三，清单用中文写，而 `assets/` 里的技能正文是英文，两边的术语要人工对齐（例如 `starting level`、`one step`）。

重新考虑的条件：如果上游同步变成多人协作，清单的合并冲突会变多，那时应改为按能力维度拆成多个小文件；如果 `capabilities.ts` 的类别集合发生变化，`LEDGER_CATEGORIES` 与清单的判定规则表要一起改，这个耦合点值得在下一次结构变动时重新评估。
