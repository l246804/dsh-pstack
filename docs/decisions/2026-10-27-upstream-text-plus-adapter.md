# 决定：技能正文保留上游原文，宿主差异只写在 `docs/harness/dsh.md`

Status: accepted
Date: 2026-10-27

## 背景

这个仓库把 pstack 移植到 DSH。V2 采用的机制是"生成期语义改写"：`scripts/patches.ts` 里有 322 条带精确锚点的文本 patch，把每个技能里的 `Task`、`readonly: true`、`~/.cursor/rules/pstack-models.mdc`、`/loop` 逐句改成 DSH 的说法，再把结果提交进 `assets/`。同一批事实还被写进另外三处：`scripts/capabilities.ts` 生成的 `assets/docs/harness/dsh.md`、手写的 `docs/upstream-divergences.md`、以及 `README.md` 的一节。

这套机制跑通了，但它的失败方式可以从提交历史里数出来。差异清单的降级表里，`image generation` 整行缺席，位置被一条本该属于 `excluded` 的 `Cursor Automations` 顶着，总数仍是 13，计数门全绿；`mapped` 的列举少一个 `agent store`，没人发现。修法是加成员级锚点，代价是每加一行能力要手写一个锚点字符串，而锚点守的是"有没有点名"，不是"点得对不对"。

更根本的问题是上游怎么做的。上游 `cursor/plugins` 给 Claude Code 适配时，生成器只做三件事：给 23 个技能插入同一行指针、把 7 个指向树外文件的相对链接改指 GitHub、复制 guide。**技能正文一个字都没改**——它的 `docs/guide/01-setup.md` 在 Claude Code 树里仍然写着"在 Cursor 聊天里运行 `/add-plugin pstack`"和"写入 `~/.cursor/rules/pstack-models.mdc`"。所有语义映射集中在一份手写的 `pstack/docs/harness/claude-code.md`（5.6KB，纯对照表），agent 每次会话读一次，自己映射。

上游能这么做是因为它把翻译放在读取时。本仓库把翻译放在生成时，于是上游每改一句话，都需要有人判断那 322 条 patch 是否仍然成立。这正是用户最初问题的来源：两份（实际是三份）文档说的对不上，因为同一个事实有四个来源。

## 决定

**技能正文保留上游原文。宿主差异只写在 `docs/harness/dsh.md` 一处。**

`docs/harness/dsh.md` 是手写的源文件，由生成器原样拷进 `assets/`。它是 `assets/` 里唯一一份不由上游派生的文档，也是唯一记录宿主差异的地方。

生成器只剩四个机械变换，都能用一句话说清，都不需要判断语义：

1. **收窄 frontmatter**。上游声明 `icon`、`color`、`paths`、`is_background`，DSH 的加载器一个都不读，因此丢弃，而不是让模型以为自己设置成功。
2. **改指树外链接**。`make-bot-ui` 不随包，`automations/`、`README.md`、Claude Code 适配文档也不随包，这些链接在安装后的包里会悬空。改指上游 GitHub 上的同名文件，保留读者本来要追的引用。
3. **插入指针**。每个正文用到 Cursor 名字的技能，在 H1 下插入一行，指向 `docs/harness/dsh.md`。这是上游 Claude Code 树的同一个机制，同一位置，同一目的：告诉读者正文是上游措辞、翻译在哪里。
4. **拷入适配文档**。

**覆盖度由 `scripts/adapter.ts` 从实际随包的正文反推**。它扫 `assets/` 里每个 Markdown 文件，收集用到的 Cursor 概念，要求 `docs/harness/dsh.md` 里有一条对应的表格行，缺哪条就报哪条，并说明读者少了这条会付出什么代价。新加一个技能说 `/visualize`，构建会失败直到适配文档给出 `/visualize` 一行。

匹配的是**表格行**，不是文档里的任意子串。这一条是实测出来的：最初的实现只查子串，于是 `Task` 那行被删掉后检查仍然通过，因为另一条讲模型 slug 的行里出现了 "Task tool"。同一次实测还发现 `resume` 被 agent store 行里的 "resumes" 误匹配。

## 备选方案

- **保留生成期改写，只把四处文档合并成一处。** 放弃：四个来源确实降到两个，但 322 条 patch 仍然要跟着上游走，而 patch 的失效方式是锚点不再匹配（构建失败，可见）或锚点仍然匹配但语义已变（静默出错）。用户指出的"后续维护是不是容易丢"指向的是后者。
- **沿用上游的运行时映射，但把适配文档做成生成的。** 放弃：生成器能渲染表格，不能判断"子代理没有沙箱时 `readonly: true` 该怎么办"。把这一行做成生成物，等于把判断放回代码里，正是这个形态想移走的东西。
- **继续用 `docs/upstream-divergences.md` 记录差异，适配文档只放工具对照。** 放弃：这会把"同一事实写两处"重新建立起来。差异清单和适配文档回答的是同一个问题（这里和上游哪里不一样），分成两份就会漂移——已经漂移过两次。
- **让检查断言适配文档的措辞与正文一致。** 放弃：那需要自然语言理解。能机械断言的边界是"正文用到的概念在文档里有点名的行"，这条边界之内的工作由 `scripts/adapter.ts` 承担；再往前一步就是用一条会过期的规则校验另一条会过期的规则。
- **只对改动过的技能插入指针，其余保持纯拷贝。** 放弃：指针的判断标准是"正文是否用到 Cursor 名字"，这是内容属性而不是改动历史。按改动历史判断会让一个从未被 patch 过的技能（例如新同步进来的）在用到 `Task` 时没有指针。实测结果是 55 个技能里 23 个需要，与上游 Claude Code 的 23/56 同量级。
- **把 `make-bot-ui` 也随包，正文说明它在这里用不了。** 放弃：它的每一步都需要 webhook 入口、routine id 和唤醒调用，没有等价宿主能力，随包只会得到一份"每一步都说做不到"的空壳。排除后那两处链接改指上游原文。

## 后果

上游同步变成"重新跑生成器"。上游改任何一句话都不需要重新判断 patch：正文跟着变，适配文档不动，覆盖度检查只在**新概念**出现时失败。技能正文读起来是 Cursor 的说法，这是明知代价：读者必须读一次适配文档，指针就是为此存在的。

代价四条。

第一，**读者多一次读取**。每个用 Cursor 名字的技能开头都有一行指针，读者要先读 `docs/harness/dsh.md`。这是上游 Claude Code 树的同一个代价。

第二，**静态门不再能证明"随包正文说的就是 DSH"**。`check:assets` 现在能证明的是：生成树可由上游重建、每个用到的概念在适配文档里有点名的行、随包链接不悬空、属于本仓库自撰的文案（README、适配文档、角色文件示例、内置 CLI）不承诺本宿主没有的东西。它不能证明某个技能里的 `Task` 被正确理解——那由读者按适配文档完成。

第三，**测试体量下降**。删掉了断言改写文本的用例。`tests/adapter.test.ts` 有 10 条，守的是覆盖度推导和变形（删一行要点名失败、散文里的偶然提及不算一行）。总体从 412 条降到 407 条，但删除的约 5 条和新增的 10 条不是同类：前者断言"这段改写文本存在"，后者断言"缺行时必须失败"。

第四，**适配文档较长**。约 120 行，37 条必需的表格行，加工具、CLI、模型与档位、路径、宿主特性、以及"步骤跑不了时怎么办"六节。它一次读完就是全部差异，这一点比它欠短更重要。

重新考虑的条件：如果 DSH 出现一个稳定的、可被模型在读取时调用的能力查询接口（例如一个列出当前可用工具与参数的元数据服务），适配文档的工具对照表就应该改成由那个接口提供，文档只保留判断性内容（`readonly` 怎么办、`/loop` 换成什么）。如果上游开始按宿主拆技能正文（而不是生成 + 适配文档），那本记录的第一条前提就不成立了。
