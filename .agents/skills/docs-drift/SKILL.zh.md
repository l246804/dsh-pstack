# 检查项目文档漂移

将项目持续维护的文档与当前证据对照，然后以只读报告结束，或应用经批准的文档修复。实现改动不属于本技能。

## 选择模式

- **Report：**`/docs-drift` 或 `/docs-drift report`。执行步骤 1–5，不写文件。
- **Fix：**`/docs-drift fix`。执行同样的检查，再执行步骤 6–7。调用 Fix 本身不构成写入批准。

接受可选的路径或 glob，用于增加或收窄候选集合，也接受可选排除项。请求的模式或范围有歧义时先询问。

## 1. 发现维护中的文档

从实际存在的根 agent 文档和根 README 开始，包括链接到的语言版本。记录缺失的入口，不创建替代文件。

读取项目维护规则，跟随将文档指定为 agent 必须阅读、更新或保持同步之对象的指针。使用项目真实的文档名称与位置；常规架构、术语或决策文档路径只是调查线索，不是必备条件。普通链接可以作为证据或接受链接检查，但不因此递归加入全文巡检。

将显式路径、glob、收窄和排除应用于候选集合。“整个仓库”只扩大候选发现范围，不使仓库内每份文档都成为项目维护文档。读取管辖每份候选文档的嵌套 agent 指令。

根据项目指针、管辖指令、归属及更新约定给每个候选文档分类：

- **维护文档：**由本项目所有，并随项目实现或工作流迭代更新。执行全部五类检查。
- **仅作参考：**依赖、宿主产品、程序库或其他外部系统的说明文档，即使存放在仓库内。只用作证据，不检查其自身漂移。
- **已排除：**不在请求范围内，或被显式规则排除。
- **未决：**维护归属不明确。纳入前先询问，同时继续分类无关候选文档。

按证据判断维护归属，不按路径、目录名、文件类型或文档主题推断。项目自己的组件文档可能属于维护文档，附带的组件库文档则可能仅作参考。管辖指令文件也只有符合同样的归属规则时才纳入维护文档集合。

生成、vendored 和上游内容不进入可编辑集合。相关发现须记录权威来源或上游去处，以及项目的生成流程（如有）。记录失效指针目标和仅用于取证的链接。每个候选文档都有分类或未决问题，且维护、参考、排除和可编辑边界都有来源依据时，本步完成。

## 2. 建立证据清单

阅读每份维护文档及管辖它的指令。盘点其中关于当前模块、职责、路径、入口、命令、工具、配置、依赖、接口、行为、数量和状态的可核验陈述。

把这些陈述追溯到当前代码、配置、清单、真实目录、入口与相关测试。文档提到的路径只是调查线索，不是证据本身。现有只读项目检查能够回答具体证据问题时加以使用。

区分当前事实、预期要求与历史陈述。当前实现证明现状，不证明行为正确。仓库无法提供充分证据时，将陈述标为未核验。

每份维护文档中的每项可核验陈述都有来源依据的处置结果或明确的证据限制时，本步完成。

## 3. 执行全部五类检查

**实现漂移。** 查找关于架构、行为、路径、命令、接口、配置、依赖、数量和状态的过时段落，或与当前证据冲突的陈述。

**矛盾。** 查找同一文档内部或跨文档的互斥陈述。区分真正矛盾与有意采用的不同详略层次。

**术语。** 查找一个概念使用冲突名称、一个名称指代不兼容概念，以及定义偏离实际用法的情况。检查有意的语言版本是否保持对应含义。

**链接与指针。** 从引用所在文档解析仓库相对链接、路径与锚点。条件允许时检查外链；网络或访问失败归为未核验，不直接判为死链。

**冗余与无依据扩写。** 查找语义重复、规则散落、过时段落，以及持续迭代中积累的无依据事实、假设与臆造扩写。例子包括虚构的模块职责、命令行为、配置默认值、设计理由、兼容性、性能结论、测试覆盖与验收状态。将已证伪或无依据的扩写收缩为有证据支持的最小陈述；仅证据不足时标为未核验，不作为删除候选。历史陈述和明确的未来计划保留其语境。

提出合并前确定权威位置。保留有意的摘要、面向不同读者的视图、语言版本与独有限定条件。

文风、格式或完整性偏好只有构成上述发现时才报告。每份维护文档都执行过全部五类检查，且每项潜在发现都有位置、当前陈述、支持证据或证据边界及建议动作时，本步完成。

## 4. 判定权威并分类发现

按问题类型确定权威：

- 用户明确要求决定预期行为。
- 当前项目规格与有约束力的约定决定其声明的限制。
- 可核验的实现证据决定当前行为的描述。
- 文档的历史语境决定过去事件的表述。

证据能够确定当前事实，且编辑只纠正描述、消除真正冗余或清理无依据扩写时，适合修复文档。

出现下列情况时停止处理该项并询问用户：

- 实现可能有误，而文档可能表达的是要求。
- 修复会改变功能、公开契约、验收标准或既定约束。
- 要求、规格、测试与实现支持互不兼容的答案。
- 证据不足或相互冲突。
- 修复需要修改实现、生成产物、vendored 内容、上游内容或受保护来源。
- 已有未提交改动使预期状态无法确定。

继续只读检查无关项，但未决项不进入修复计划。每项潜在发现都归为可修复、需要用户决定或未核验，且每项可修复动作都只涉及文档时，本步完成。

## 5. 报告

报告候选范围与维护文档范围、归属证据、仅作参考的文档、排除项、失效指针目标、证据限制和每份维护文档的处置结果。未决问题与未核验陈述保持可见，不计为无问题。

每项发现使用以下结构：

```text
[实现漂移 | 矛盾 | 术语 | 链接 | 冗余] 标题
  位置：<文档>:<行号或章节>
  现状：<陈述、重复内容或无依据扩写>
  证据：<来源与观察到的事实，或证据边界>
  建议：<仅文档纠正、删除或合并>
  处置：可修复 | 需要用户决定 | 未核验
```

冗余发现须写明拟定的权威位置，以及其他位置分别保留、合并或链接什么。无依据扩写须说明是删除，还是收缩为有证据支持的陈述。无需关注时明确说明，并列出仍存在的未核验项。

Report 到此结束，不写文件，也不创建报告产物。每份维护文档和每项潜在发现都有已报告的结果，且每个候选文档都有已报告的分类或未决问题时，本步完成。

## 6. 批准并修复

Fix 按文件和发现分组展示精确的拟修改内容。实质改写、删除或合并须展示精确的替换文本或删除边界，并覆盖所有受影响语言版本。单独标明因未决问题而排除的修改。

请求明确批准并等待。用户可以只批准其中一个子集。严格应用获批修改，保留无关内容与用户已有改动。

证据支持时，修复权威来源并同步有意的摘要与语言版本。生成结果使用项目的生成流程。合并必须保留每项独有要求、约束、注意事项与证据指针。出现新的语义冲突时停止该项并请求新的决定，不借此扩大获批范围。

每个获批项都已严格应用，或明确保持未应用并说明原因，且没有未获批文件变化时，本步完成。

## 7. 核验并收尾

重新阅读每份修改过的文档。确认获批发现已解决、链接可解析、对应语言视图一致、合并内容仍可追溯，且没有未批准的语义变化。

运行相关的现有项目检查并记录实际结果。报告修改文件、已解决发现、获批保留项、未决问题、未核验陈述与验证证据。没有获批或需要修改的内容时，明确说明没有文件变化。

每项获批修改都有验证证据或具体的剩余失败，且每项检查都有实际结果时，本步完成。
