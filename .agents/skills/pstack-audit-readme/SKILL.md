# 审查并重建 pstack/README.md

交付可复现、逐条取证的独立调查。先读 [`../pstack-porting-contract.md`](../pstack-porting-contract.md) 并全程执行；唯一目标文件是 `pstack/README.md`。

## 1. 清点需求与模板

确认两个上游路径并记录提交。用文件枚举工具清点 `<pstack>` 下全部 `*.md`、`*.mdc` 及文档形式的 agent/automation 模板与提示，逐份读取。按出现顺序登记“来源文档 + 章节/条目 + 原始要求”；重复需求先保留，清点完成后归并并保留全部来源。每份文档都有能力条目或“无可移植能力”标记，搜索命中不能替代全量清点。再完整读取 `upstream/cursor-plugins/pstack/docs/harness/claude-code.md`，登记其标题、引导段、章节顺序、表格列、条目粒度和说明方式。

第 3 步冻结结论前，读取范围限于上游需求文档、证明 DSH 能力所需的 `<dsh>` 内容和仓库 `docs/` 约定；现有移植源码、生成树和旧 README 留待后续规定阶段。

完成标准：每份文档均有原子能力条目或“无可移植能力”标记，重复需求保留全部来源；模板结构逐项有位置记录。

## 2. 逐项取得 DSH 证据

按契约先执行平台排除，再将保留能力归入映射、标准模式或可选插件。调查 `<dsh>` 时：

- 从实际入口、工具/事件/服务声明、配置 schema、包导出、插件 manifest、默认启用状态和测试追踪行为，记录版本与准确插件 ID。
- 分开调查标准模式与显式开启的可选插件；实验性插件归入可选插件层。
- 比较目标行为、生命周期和关键语义，而非名称相似性。
- 按契约为第 2、3 层记录支持范围、缺口、场景、建议和证据。

完成标准：每项能力恰有排除结论或一个主层；第 2、3 层的每条支持与不支持的陈述均有可打开的 DSH 文件行链接，每个缺口均有场景与建议；证据不足项显式保留为未决。

## 3. 冻结并自审结论

建立能力追踪表，逐项回查文档清单和 DSH 原文。重点核对上游新增能力是否已由 DSH 覆盖，以及上游已移除行为是否仍误列在范围内。

完成标准：每项能力恰有一个去向，全部第 2、3 层结论和缺口经原文复核；插件内实现集合只含 DSH 仍不完整的行为；此时尚未读取 `pstack/src/`、其他现有实现或旧 README。

## 4. 重建 README

取得 `pstack/README.md` 的文件状态；存在时现在读取，仅用于保留仍适用的项目导航和满足写前读取要求。正文结论均由本轮上游与 DSH 证据独立得出。

沿用上游 `claude-code.md` 的组织方式撰写 DSH 版移植说明，保留引导说明、同类映射表和特性差异表达；新增内容仅承载调查所需的支持范围、证据、缺口、场景和建议。写入两个上游提交，并至少建立以下可追踪内容：

1. **等价映射**：上游名称、字段或路径到 DSH 对应项及必要语义说明。
2. **标准模式覆盖**：完全与部分覆盖分开；每项含支持范围、缺口、场景、建议和 DSH 证据。
3. **可选插件覆盖**：准确插件 ID、实验性状态、启用条件、完全或部分覆盖；每项含支持范围、缺口、场景、建议和 DSH 证据。
4. **插件内实现范围**：仅列仍不完整且确需本插件提供的能力，保留原子能力编号与验收行为，以待实现语义表述；平台排除项及其局部步骤不进入此集合。

按契约引用上游需求与 DSH 实现，证据精确到行；本仓自身结论不能充当证明。

完成标准：全部原子能力均有去向，每个第 2、3 层条目具备所需场景与证据；待实现集合不含映射、配置、平台排除项或 DSH 已有能力，实现状态均由本轮调查确认。

## 5. 验证并报告

重新打开全部证据，核对路径、行号和含义；回查文档来源去向，验证 README 相对链接可解析。报告上游提交、文档与能力计数、各分类计数、插件内实现项、未决证据和输出路径。

本次只生成调查文档。无法证实的关键能力保留醒目标记并在报告中列出。
