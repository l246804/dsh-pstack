# pstack 移植契约

供 `pstack-audit-readme`、`pstack-implement-readme`、`pstack-write-dsh-doc` 三个手动技能共同执行。`<root>` 表示仓库根目录，相对路径均从 `<root>` 解析。

## 1. 冻结证据基线

每轮只从以下来源形成产品事实、分类、设计和文档结论：

- `upstream/cursor-plugins/pstack/`：被移植的 pstack，记为 `<pstack>`。
- `upstream/deepseek-harness/`：DSH 参考实现，记为 `<dsh>`。
- `docs/`：本仓架构、术语和决策约定。
- 当前技能明确指定的输入与目标文件。

其他现有移植源码、生成树、旧文档、测试、构建产物和历史结论不参与取证。`AGENTS.md` 与技能文件是操作指令，不是产品能力证据。读取配置获取命令或依赖时，也只提取对应事实。

分派只读子任务时，逐条列出允许与禁止读取的路径；主任务打开原证据核验后，才可采用子任务结论。证据范围不因子任务、网络资料、记忆或本机其他版本而扩大。

记录并绑定两个上游提交：

```bash
git -C <pstack> rev-parse HEAD
git -C <dsh> rev-parse HEAD
```

任一目录缺失、证据不可读或提交不符时，报告具体路径与提交状态，等待用户提供预期检出。`<pstack>` 的 Markdown 声明待移植需求与行为；`<dsh>` 的源码、类型、包清单、插件声明和测试证明 DSH 能力，示例或注释不能单独作为能力证据。

## 2. 使用稳定原子能力编号

将复合要求拆到可独立判定支持程度的**原子能力**：一次工具调用、字段的一种取值、一条路径约定或一个平台动作分别成项。每项使用跨分类、实现和验收保持不变的稳定编号；编号只标识需求，不表示需要插件代码。

## 3. 先排除，再分三层

沿用 `<pstack>/docs/harness/claude-code.md` 的 `Cursor-only features` 作为平台取舍基线。识别其中跳过的 Cursor Automations、云代理控制面及绑定的例程、webhook、唤醒、秘密请求、云端状态和机器操作，按**完整能力**判定：

- DSH 源码证明端到端等价支持：进入三层分类。
- 仅有局部相似能力、仍依赖云服务或证据不足：登记“按上游平台排除基线舍弃”及模板行，不进入缺口分析或插件内实现范围。

局部能力不能拼成完整支持；`create_goal`、定时调度、本地子代理和 worktree 等只能证明各自行为，不能证明 Cursor Automations 或云代理支持。舍弃项仅沿用上游的跳过、继续后续步骤和占位符处理。模板明确保留的替代流程仍正常分类，例如普通 PR 评论按 forge 命令处理，`environment: "cloud"` 仅按模板映射为本地 worktree；这些本地流程不扩大为云端能力。

其余每项原子能力恰有一个主层；跨层行为拆成独立子项：

1. **映射**：DSH 标准模式已有完整等价功能，只需转换名称、字段、路径或调用方式；目标行为、生命周期和关键语义一致，无需新增运行时能力。
2. **标准模式**：DSH 在未启用本仓插件及其他可选插件时提供的能力。标明完全或部分覆盖，部分覆盖明确剩余缺口。
3. **可选插件**：启用 `<dsh>` 提供的可选插件后获得的能力，包括实验性插件。记录准确插件 ID、启用条件、默认状态及完全或部分覆盖。

每项记录“上游期待 / DSH 实际 / 结论 / 证据”。第 2、3 层另记支持行为、未支持行为及精确启用或调用条件。只有这些层仍不完整的行为进入“插件内实现”集合；该集合是实现阶段的完整范围。

## 4. 证据链接与缺口

证据指向固定提交中的真实文件与行。输出内使用可从目标文件解析的相对链接：

`pstack/README.md`：

```text
[`上游相对路径#L起-L止`](../upstream/<上游路径>#L起-L止)
```

`pstack/overlay/docs/harness/dsh.md`：

```text
[`上游相对路径#L起-L止`](../../../../upstream/<上游路径>#L起-L止)
```

面向托管仓库发布时，将同一文件、行号和已记录提交改写为提交永久链接。文件变化后重新核对行号；路径不存在、行号越界或引文不支持结论即为无效证据。

否定结论写明搜索范围、最接近的实现证据和缺失点，并限定于当前提交与调查范围。证据不足统一标为“当前提交未证实”。

第 2、3 层的每个部分覆盖或未覆盖缺口分别写明：

- **支持什么**：代码可证实的 DSH 行为及使用条件。
- **不支持什么**：相对上游缺少的具体语义、输入、状态或生命周期。
- **场景示例**：上游步骤、输入或配置、期望结果、DSH 实际结果或阻断点，并绑定能力编号。
- **建议**：可执行的 DSH 映射、插件启用、插件内实现、工作流调整或人工介入点。

完全覆盖也记录支持范围与证据，无需缺口字段。

## 5. 交付前追踪审计

逐项回查完整清单：

```text
上游文档条目 → 原子能力编号 → DSH 分类与证据 → 插件实现或明确无需实现 → 本阶段产物位置
```

报告未覆盖、证据不足和有意跳过项；为空时明确写“无”。完成以每项来源、分类、证据和产物去向均可回查为准。
