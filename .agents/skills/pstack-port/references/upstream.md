# upstream：更新上游并评估影响

用于 pstack 或 DSH 上游更新。产物是更新后的检出和唯一影响结论；本分支不运行构建、不启动后续分支，也不生成额外交接文件。

## 1. 确认范围与目标

让用户选择更新 pstack、DSH 或两者，并确认各自目标提交或版本。用户未指定目标时，先展示远端默认分支的最新提交，再请求确认。分别记录当前提交与目标提交，不把其中一个上游的更新绑定到另一个。

检查对应上游工作区与当前仓库状态。上游有未提交改动、目标不明确或更新会覆盖用户工作时，停止并报告具体路径与状态。`docs/port-review.md` 存在活跃轮次时，先完成或由用户明确放弃并由 `audit` 重置，再更新上游，避免审查证据被上游变化污染。

完成标准：更新范围、目标提交和当前状态均已确认；本地改动风险已处理。

## 2. 更新检出

在对应上游仓库 fetch，并检出已确认的目标。逐项检查命令退出码，更新后记录实际 HEAD 和本仓 submodule 状态；不代为提交，不直接编辑上游内容文件。

所有选定上游均已处于目标提交时，报告“无实质更新”并停止，不启动影响评估。目标提交发生变化时才继续。任一上游更新失败时，报告已更新与未更新的项目，不评估未确定的基线。

完成标准：每个选定上游均处于已确认提交，或已报告无变化；实际 HEAD 与本仓状态可回查。

## 3. 只读影响评估

比较新旧提交及行为差异，读取当前有效产物：

- `docs/port-prepare.md` 的结构与生成链基线。
- `pstack/README.md` 的需求、实现和最终覆盖状态。
- `pstack/harness/` 的当前适配文档。
- 当前 runtime、插件实现与构建配置。

`docs/port-review.md` 不是分流依据；完成后的当前事实以 README、harness 和实现为准。核对 `docs/port-prepare.md` 和 README 是否仍记录旧提交：结构报告偏差交回 `prepare`，需求或能力事实偏差交回 `audit`，避免后续阶段混用新旧证据。

按以下优先级给出唯一建议：

1. **从 `prepare` 开始**：目录、本地适配树、runtime 镜像或生成替换机制受影响。
2. **从 `audit` 开始**：上游需求、脚本行为、DSH 公共能力、插件组合或权限事实变化，结构无需先整理。
3. **只构建**：README 与 `docs/port-prepare.md` 记录的提交均未变化，变化只要求重新复制或生成产物，当前适配规则、实现、行为和验证依据均未改变。
4. **无需后续动作**：没有实质影响。

上游需求或 DSH 能力事实变化时，即使影响很小也重新执行 `audit`；`implement` 随后保留符合新基线的现有实现，只修改受影响部分。

完成标准：每项变化都有影响结论与证据；建议入口唯一且符合上述优先级；没有把构建当作需求或行为审查的替代。

## 4. 报告并停止

报告更新范围、新旧提交、变化清单、影响评估、建议入口及理由。只构建时给出根目录构建命令，不代替用户执行；建议 `prepare` 或 `audit` 时等待下一次显式调用。本分支只报告分流结果，不生成额外交接文件。

完成标准：更新范围、新旧提交、变化、影响与唯一建议均已报告；没有执行构建或后续分支。
