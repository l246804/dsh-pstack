# upstream：更新上游并评估入口

用于 pstack 或 DSH 上游更新。只确认范围、更新检出、评估影响并报告建议入口；不自动执行构建、`prepare` 或 `audit`，不新增跨阶段状态文件。

## 1. 确认更新范围与目标

请用户明确选择更新 pstack、DSH 或两者，并确认各自目标提交或版本；用户未指定目标时，先展示将使用的远端默认分支最新提交，再请求确认。两个上游分别记录当前提交与目标，不把其中一个的更新绑定到另一个。

检查对应上游工作区与当前仓库状态。上游存在未提交改动、目标不明确或更新会覆盖用户工作时，停止并报告具体路径与状态。

完成标准：更新范围、目标提交和当前状态均已确认；没有未处理的本地改动风险。

## 2. 更新上游检出

在相应上游仓库 fetch，并检出已确认目标。逐项检查命令退出码，更新后记录实际 HEAD 和本仓 submodule 状态；不代为提交，不直接编辑上游内容文件。

所有选定上游均已处于目标提交时，报告“无实质更新”并停止，不启动后续流程。目标提交发生变化时才继续影响评估。任一上游更新失败时，报告已更新与未更新的项目，不继续评估未确定的基线。

完成标准：每个选定上游均处于已确认提交，或已报告无变化；实际 HEAD 与本仓状态可回查。

## 3. 只读影响评估

比较新旧提交及行为差异，读取当前有效产物：

- `docs/port-prepare.md` 的结构与生成链基线。
- `pstack/README.md` 的需求、实现和最终覆盖状态。
- `pstack/harness/` 的当前适配文档。
- 当前 runtime、插件实现与构建配置。

本轮实现闭环的 `docs/port-review.md` 不作为分流依据；完成后的当前事实以 README、harness 和实现为准。

核对 README 和结构报告是否仍记录旧提交；存在基线提交偏差时先按分流入口更新，不让后续阶段混用新旧证据。

按以下优先级给出唯一建议：

1. **从 `prepare` 开始**：目录、本地 harness 适配树、runtime 镜像或生成替换机制受影响。
2. **从 `audit` 开始**：上游需求、脚本行为、DSH 公共能力、插件组合或权限事实变化，结构无需先整理。
3. **只构建**：变化只要求重新复制或生成产物，当前适配规则、实现、行为和验证依据均未改变。
4. **无需后续动作**：没有实质影响。

上游需求或 DSH 能力事实发生变化时，即使影响很小也重新执行 `audit`；`implement` 随后保留符合新基线的现有实现，只修改受影响部分。

完成标准：每项变化都有影响结论与证据；建议入口唯一且符合上述优先级；未把构建当作需求或行为审查的替代。

## 4. 报告并停止

报告更新范围、新旧提交、变化清单、影响评估、建议入口及理由。只构建时给出根目录构建命令，不代替用户执行；建议 `prepare` 或 `audit` 时等待下一次显式调用。本分支只报告分流结果，不生成额外交接文件。
