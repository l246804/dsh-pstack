# implement：实现能力并修复审查发现

交付 README 插件内实现范围内的代码及必要的生产依赖。先冻结需求、既定适配与 DSH API 方案，再读取现有实现；从 `docs/architecture.md` 确定当前手写实现位置。`docs/extensions.md` 中 `proposed` 与 `active` 条目是独立保留范围，其增量开发交给 `/pstack-port feature`。

## 1. 选择模式并冻结基线

完整读取 README，提取原子能力、分类、实现范围、验收行为和分阶段状态；读取 `docs/extensions.md`，登记保留范围。README 与当前上游提交不符，或缺少能力编号、分类、实现范围、所需证据时，停止并报告需要重新运行 `/pstack-port audit`。

读取 `docs/port-review.md` 并选择模式：

- **审查修复模式**：存在 `open` 或 `reopened` findings。
- **实现模式**：没有开放 findings，且报告缺失、为 `audit` 新建的初始报告，或不含 `closed`/`fixed-pending-review` findings。
- **等待复核**：报告只有 `closed` 或 `fixed-pending-review` findings 时，不重新实现，报告状态并等待 `review`。

审查修复模式只处理开放 findings 及其受影响调用方、权限边界、组合行和测试，建立“finding ID → 能力 ID → 文件/行 → 修复动作 → 验证”的清单。报告与 README 基线不符时停止；finding 的代码或证据已变化时，先交回 `review` 重新确认。

逐项复核 README 的既定适配与对应决策。既定适配不再生成候选；确需改变长期选择时停止，交回新决策与 `audit`。每项实现建议必须是“已选择”或“证据唯一”；存在“待选择”时，展示候选、限制与取舍，取得用户确认后更新该选择记录再继续。

读取现有实现前，用 `<pstack>` 文档及脚本和 `<dsh>` 源码复核宿主接口及待实现范围，冻结需求基线。

完成标准：模式与处理范围明确；每个待实现项或开放 finding 都有上游行为、目标接口和可观察验收结果；既定适配均有验收要求；只有真正未决的方案需要确认；基线尚未受旧实现影响。

## 2. 核对公共接口、组合与依赖

对每个宿主交互点，沿 `<dsh>` 的正式导出、类型声明、SDK、插件包和调用示例确认公共接口；读取实际包的 `package.json`、导出类型与实现，区分宿主内部能力和公共 SDK。

按优先级选择实现：

1. 复用可由依赖包导入的 DSH SDK、类型、schema、协议辅助函数和工具实现。
2. 通过本 bundle 的声明式组合复用 DSH 插件与服务。
3. 使用有源码证据的公共插件接口。
4. 上述方式仍不覆盖缺口时，在架构规定的手写位置实现插件专属逻辑，以最小接口隔离。

为每个所需 DSH 插件建立组合表：能力、插件包与行 ID、服务或工具、宿主已启用时的复用方式、宿主未启用时的 bundle 行、互斥行、验证环境。宿主已有行保持其配置，缺失的必要行随本 bundle 启用；互斥只处理同一组合中的重复或冲突，保留服务提供者与消费者完整性。公开 API 不能表达所需条件时，记录限制并选择最小的声明式方案。

发布源码导入的 DSH SDK、运行时服务包和类型声明包均放入根 `package.json` 的 `dependencies`；构建、测试和仓库维护工具才放入 `devDependencies`。类型包作为生产依赖时，不通过打包配置把它隐藏或内联。使用 `<dsh>` 证明的准确包名及兼容版本，遵循工作区 catalog/版本协议，更新锁文件并确认实际安装；依赖来源使用包声明，而非 `<dsh>` 相对路径。构建配置只承担编译与资源组装。

完成标准：每个宿主交互都有 DSH 源码位置和导入来源；每个所需插件都有已验证的组合与冲突处理；每项发布运行或类型依赖都在 `dependencies`；手写声明均无法由已确认 SDK 替代。

## 3. 对照现有实现

需求基线和 API 方案冻结后，读取架构指出的入口、本地 harness 适配树、runtime 等手写实现，逐文件判定：

- **保留**：行为符合基线且未重复 DSH 能力。
- **修改**：接口、行为、依赖或权限与当前证据存在明确偏差。
- **新增**：基线要求但尚不存在。
- **删除**：重复 DSH 能力、处理上游已移除行为、依赖不存在的宿主接口或仅服务旧抽象。

既有 Node 脚本、模型路由等符合既定适配的实现以保留和核验为起点；有行为偏差才修改。需要重建时，先列出拟删除文件和符号，解析绝对路径并确认均位于契约允许的手写范围内，再清理并按已确认方案重建。保留 `proposed` 与 `active` 扩展条目，以及每个 `active` 扩展的实现和回归验证。

完成标准：每个待实现项映射到具体保留、修改或新增动作；每个既定适配均有源码与测试核验；每个重复或过时行为有处理结论；需求集合与冻结基线一致。

## 4. 实现并建立行为与权限验证

实现模式只实现 README 的插件内实现集合；审查修复模式只处理开放 findings。两种模式都保留本地扩展并遵守写入边界，DSH 文本差异集中在本地 harness 适配树，由 `doc` 编写。

遵循 `docs/architecture.md`、`docs/glossary.md` 和相关决策约定；架构边界、入口或术语变化时同步更新。实现公共接口、输入校验、生命周期、清理、错误传播和用户可见行为，使其符合上游场景与 DSH 语义；类型以声明包为准。

每个模型可触发的操作都按契约进入对应 DSH 执行面。逐一核验 sandbox、审批、取消、超时、后台任务和工作目录语义；脚本执行尤其要检查直接 `spawn`、shell、文件、网络和外部命令。没有保留这些边界的公共接口时，按契约记录安全阻断并请求方案选择。

为每个 README 缺口建立公共行为的可执行验证，覆盖具体场景、边界和失败路径。为既定适配增加回归用例，包括带多级 `/` 的完整模型 ID 和每个 Node 脚本的真实调用。按操作适用面验证权限拒绝、批准、只读、越界与取消。runtime 按契约保持上游行为，确有差异时记录到对应能力状态。

完成标准：每个实现项均有对应代码和至少一个行为验证；每个既定适配与 `active` 本地扩展的回归验证保持有效；所有宿主交互使用已核实的公共导入或接口；DSH 已覆盖能力没有替代实现；所有模型触发副作用均有经过验证的权限边界。

## 5. 验证、记录并停止

执行最窄的相关测试、类型检查和构建，再执行受影响工作区及真实安装环境验收；runtime 不增加独立类型检查门禁。逐项检查退出码，区分本次失败、环境问题和既有失败；本次未解决失败不得报告完成。

真实安装至少覆盖所需 DSH 插件未启用、已由宿主启用两种初始组合；存在互斥时增加冲突状态。检查 bundle 行、服务可用性、工具可见性和重启后的新会话行为，不以 package 安装成功代替能力验收。

核对生产依赖、锁文件、实际解析位置与源码导入一致。只更新 README 中本次涉及能力的实现状态区，记录实现位置、实际行为、验证结果和剩余限制。

审查修复模式只在对应 finding 记录下追加本轮修复与验证：验证完成标为 `fixed-pending-review`，未通过标为 `open` 并保留原因；其他 findings、审查轮次、文件哈希和关闭记录保持原状。仍有开放 findings 时，报告继续修复，不宣称本轮实现完成。

建立最终追踪表：

```text
README 能力编号/finding ID → 既定适配/公共接口 → 实现文件 → 行为与权限验证 → 未解决限制
```

报告模式、处理的 finding ID、实现变化、插件组合、生产依赖及全部验证结果。报告后结束本分支，等待用户显式调用 `review`。
