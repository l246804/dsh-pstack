# implement：实现 README 规定的插件能力

交付 README 插件内实现范围内的代码及必要的生产依赖。先冻结需求、既定适配与 DSH API 方案，再读取现有实现；从 `docs/architecture.md` 确定当前手写实现位置，生成树与上游子模块只按架构规则维护。`docs/extensions.md` 中 `proposed` 与 `active` 条目是独立保留范围，其增量开发交给 `/pstack-maintain`。

## 1. 冻结本轮需求与既定适配

确认 `<pstack>`、`<dsh>` 和 `pstack/README.md` 存在并记录上游提交。完整读取 README，提取原子能力编号、分类、插件内实现范围、缺口场景和验收行为；读取 `docs/extensions.md`，登记独立保留范围。

逐项提取 README 的“本仓既定适配”，打开对应决策和架构原文复核。把模型路由分隔、Node 脚本运行时、源码位置等既定内容直接纳入需求基线；这些项目不再生成候选或请求重新选择。实现状态或源码差异只能改变核验与修改动作，不能推翻已接受决策；确需改变长期选择时停止，交回新决策与 `/pstack-port audit`。

README 提交与当前上游不一致，或缺少能力编号、分类、实现范围、所需证据时，停止实现并报告需要重新运行 `/pstack-port audit` 的具体原因。逐项检查实现建议状态：每项必须是“已选择”或“证据唯一”。存在“待选择”时停止，展示该项候选、限制与取舍，请用户明确选择；确认后把“已选择”、所选方案、关键边界和确认日期写回 README，再继续。

读取现有实现前，用 `<pstack>` 文档及脚本和 `<dsh>` 源码复核宿主接口及待实现范围，冻结需求基线。

完成标准：每个待实现项都有上游行为、DSH 缺口、目标接口和可观察验收结果；每个既定适配都有验收要求且未进入候选；README 与两个上游提交一致；每项实现建议均有“已选择”或“证据唯一”记录；范围尚未受旧实现影响。

## 2. 核对公共接口、组合与依赖

对每个宿主交互点，沿 `<dsh>` 的正式导出、类型声明、SDK、插件包和调用示例确认插件可用的公共接口；读取实际包的 `package.json`、导出类型与实现，区分宿主内部能力和公共 SDK。

按优先级选择实现：

1. 复用可由依赖包导入的 DSH SDK、类型、schema、协议辅助函数和工具实现。
2. 通过本 bundle 的声明式组合复用 DSH 插件与服务。
3. 使用有源码证据的公共插件接口。
4. 上述方式仍不覆盖缺口时，在架构规定的手写位置实现插件专属逻辑，以最小接口隔离。

为每个所需 DSH 插件建立组合表：能力、插件包与行 ID、服务或工具、宿主已启用时的复用方式、宿主未启用时的 bundle 行、互斥行、验证环境。宿主已有行保持其配置；缺失的必要行随本 bundle 启用。互斥只禁用在同一组合中重复或冲突的行，保留服务提供者与消费者完整性；不用运行时 profile 修改替代安装时组合。公开 API 不能表达所需条件时，记录组合限制并选择最小的声明式方案。

发布源码导入的 DSH SDK、运行时服务包和类型声明包均放入根 `package.json` 的 `dependencies`；构建、测试和仓库维护工具才放入 `devDependencies`。类型包作为生产依赖时，不通过打包配置把它隐藏或内联。使用 `<dsh>` 依赖声明和导出所证明的准确包名及兼容版本，遵循工作区 catalog/版本协议，更新锁文件并确认实际安装；依赖来源使用包声明，而非 `<dsh>` 相对路径。构建配置只承担编译与资源组装，不用来补救错误的依赖分层。

完成标准：每个宿主交互都有 DSH 源码位置和导入来源；每个所需插件都有已验证的组合与冲突处理；每项发布运行或类型依赖都在 `dependencies`；手写声明均无法由已确认 SDK 替代。

## 3. 对照现有实现

需求基线和 API 方案冻结后，读取架构指出的入口、覆盖层、运行时等手写实现，逐文件判定：

- **保留**：行为符合基线且未重复 DSH 能力。
- **修改**：接口、行为、依赖或权限与当前证据存在明确偏差。
- **新增**：基线要求但尚不存在。
- **删除**：重复 DSH 能力、处理上游已移除行为、依赖不存在的宿主接口或仅服务旧抽象。

冻结基线优先于旧代码、注释和测试。既有 Node 脚本、模型路由等符合既定适配的实现以保留和核验为起点；有行为偏差才修改。需要重建时，先列出拟删除文件和符号，解析绝对路径并确认均位于架构规定的手写实现范围内，再清理并按已确认方案重建。保留 `proposed` 与 `active` 扩展条目，以及每个 `active` 扩展的实现和回归验证；其功能变更通过 `/pstack-maintain` 处理。

完成标准：每个待实现项映射到具体保留、修改或新增动作；每个既定适配均有源码与测试核验；每个重复或过时行为有处理结论；每个保留范围均可追踪；需求集合与冻结基线一致。

## 4. 实现并建立行为与权限验证

本轮代码改动只实现 README 的插件内实现集合，并保留登记的本地扩展。DSH 标准模式或可选插件负责其已覆盖工作，本插件只实现证据规定的映射、编排和剩余缺口；平台排除项及其局部步骤保持排除。

遵循 `docs/architecture.md`、`docs/glossary.md` 和相关决策约定；架构边界、入口或术语变化时同步更新。实现公共接口、输入校验、生命周期、清理、错误传播和用户可见行为，使其符合上游场景与 DSH 语义；类型以声明包为准。

每个模型可触发的操作都按契约进入对应 DSH 执行面。逐一核验 sandbox、审批、取消、超时、后台任务和工作目录语义；脚本执行尤其要检查直接 `spawn`、shell、文件、网络和外部命令。没有保留这些边界的公共接口时，按契约记录安全阻断并请求方案选择。

为每个 README 缺口建立公共行为的可执行验证，覆盖具体场景、边界和失败路径。为既定适配增加回归用例，包括带多级 `/` 的完整模型 ID 和每个 Node 脚本的真实调用。按操作适用面验证权限拒绝、批准、只读、越界与取消。修改范围限于当前需求所需的手写实现、生产依赖和文档，`dsh.md` 留给文档分支。

完成标准：每个实现项均有对应代码和至少一个行为验证；每个既定适配与 `active` 本地扩展的回归验证保持有效；所有宿主交互使用已核实的公共导入或接口；DSH 已覆盖能力没有替代实现；所有模型触发副作用均有经过验证的权限边界。

## 5. 验证、报告并停止

从 `docs/`、环境已知命令或 package scripts 选择验证方式，执行最窄的相关测试、类型检查和构建，再执行受影响工作区的验证。逐项检查退出码；失败时区分本次实现、环境或既有问题并给出证据，本次未解决失败不得报告完成。

在至少两类初始组合中做真实安装验证：所需 DSH 插件未启用、已由宿主启用；存在互斥时增加冲突状态。检查 bundle 行、服务可用性、工具可见性和重启后的新会话行为，不以 package 安装成功代替能力验收。

核对根生产依赖、锁文件、实际解析位置与源码导入一致。建立最终追踪表：

```text
README 能力编号 → 既定适配/公共接口 → 实现文件 → 行为与权限验证 → 未解决限制
```

报告保留、修改、新增和删除的实现，插件组合与冲突处理，新增生产依赖及其 DSH 来源，以及全部验证结果。逐项确认无需实现的映射、标准模式和可选插件能力未被重写；仍无法由公共 DSH 能力实现的项目保留证据与具体阻断。报告后结束本分支，等待用户显式调用 `review`。
