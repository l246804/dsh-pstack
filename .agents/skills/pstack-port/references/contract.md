# pstack 移植契约

供 `/pstack-port` 的 `audit`、`implement`、`review`、`doc` 分支共同执行。`<root>` 表示仓库根目录，相对路径均从 `<root>` 解析。

## 1. 分开冻结三类事实

每轮分别记录来源，避免用旧实现反推需求，也避免重新决定已经落地的适配：

1. **上游需求**：`upstream/cursor-plugins/pstack/`，记为 `<pstack>`。Markdown 声明行为；被文档或技能调用的脚本声明执行入口、运行时和具体算法。
2. **DSH 能力**：`upstream/deepseek-harness/`，记为 `<dsh>`。源码、类型、包清单、插件声明和测试证明能力，示例或注释不能单独作证。
3. **本仓适配契约**：`docs/architecture.md`、`docs/decisions/` 中 `Status: accepted` 的记录、`docs/extensions.md` 的 `proposed` 与 `active` 条目。它们规定长期适配选择及保留范围，不证明上游需求或 DSH 能力。

`proposed` 决策与当前手写实现可以在分支规定的阶段用于差异或实现核验，但本身不是既定适配。`AGENTS.md` 与技能文件是操作指令，不是产品能力证据。配置只提供命令、依赖等对应事实；生成树、旧文档、测试和构建产物只证明各自直接表达的事实。

只读子任务遵循同一份路径白名单；主任务打开原证据核验后才采用其结论。网络资料、记忆和本机其他版本不扩大证据范围。

用 `git -C <pstack> rev-parse HEAD` 和 `git -C <dsh> rev-parse HEAD` 记录并绑定两个上游提交。目录缺失、证据不可读或提交不符时，报告具体路径与提交状态，等待用户提供预期检出。

## 2. 拆分并编号原子能力

将复合要求拆成可独立判定支持程度的**原子能力**：一次工具调用、字段的一种取值、一条路径约定、一个脚本运行时前提或一个平台动作分别成项。每项使用跨分类、实现和验收保持不变的稳定编号；编号标识需求，不代表需要插件代码。

## 3. 先排除，再分三层

先按 `<pstack>/docs/harness/claude-code.md` 的 `Cursor-only features` 判断上游要求排除的**完整能力**：

- DSH 源码证明端到端等价支持：进入三层分类。
- 仅有局部相似能力、仍依赖云服务或证据不足：登记“按上游平台排除基线舍弃”及模板行，不进入缺口分析或插件内实现范围。

局部能力不能拼成完整支持。舍弃项沿用上游的跳过、继续后续步骤和占位符处理。完整排除不扩散到模板明确保留的本地替代流程：普通 PR 评论仍按 forge 命令分类，`environment: "cloud"` 仍按本地 worktree 映射；这些流程不构成云端能力。

其余每项原子能力恰有一个主层；跨层行为拆成独立子项：

1. **映射**：只需转换名称、字段、路径或调用方式，即可保留完整目标行为、生命周期和关键语义。
2. **标准模式**：未启用本仓插件及其他可选插件时，DSH 提供的运行时能力。标明完全或部分覆盖，部分覆盖明确剩余缺口。
3. **可选插件**：启用 `<dsh>` 提供的可选插件后获得的能力。记录准确插件 ID、启用条件、默认状态、实验性状态及完全或部分覆盖；实验性状态是兼容风险证据，不构成文档排除规则。

每项记录“上游期待 / DSH 实际 / 结论 / 证据”。第 2、3 层另记支持行为、未支持行为及精确启用或调用条件。只有这些层仍不完整的行为进入“插件内实现”集合；该集合是实现阶段的完整范围。

## 4. 插件组合与权限边界

- 优先通过本 bundle 的声明式组合复用 DSH 插件：宿主已提供的行直接复用，缺失的必要行随本 bundle 启用；互斥行明确禁用及理由。安装后组合是一次性配置，不由模型在运行时改写用户 profile。验证两种初始状态与冲突状态。
- 模型触发的进程、文件、网络、安装和远程操作进入 DSH 对应执行面，继承其 sandbox、审批、取消和生命周期。可信插件代码的内部初始化与模型触发操作分开记录；不能用封闭脚本 ID、参数校验或文档提示代替权限执行。
- 每个手写工具列出实际副作用与所继承的 DSH 权限执行面。没有公共接口能保留必要边界时，记录安全阻断并提交最小方案选择，不以直接 spawn、直接文件访问或本插件自设旁路交付。

## 5. 证据与缺口

审查 README 的证据指向固定提交中的真实文件与行，使用可从目标文件解析的相对链接：`[上游相对路径#L起-L止](../upstream/<上游路径>#L起-L止)`。面向托管仓库发布时，将同一文件、行号和已记录提交改写为提交永久链接。文件变化后重新核对行号；路径不存在、行号越界或引文不支持结论即为无效证据。

否定结论写明搜索范围、最接近的实现证据和缺失点，并限定于当前提交与调查范围。证据不足统一标为“当前提交未证实”。

第 2、3 层的每个部分覆盖或未覆盖缺口分别写明：

- **支持什么**：代码可证实的 DSH 行为及使用条件。
- **不支持什么**：相对上游缺少的具体语义、输入、状态或生命周期。
- **场景示例**：上游步骤、输入或配置、期望结果、DSH 实际结果或阻断点，并绑定能力编号。
- **建议**：可执行的 DSH 映射、插件组合、插件内实现、工作流调整或人工介入点。

完全覆盖也记录支持范围与证据，无需缺口字段。

## 6. 交付前追踪审计

按当前分支回查追踪链；后续节点记录预定去向：

```text
上游文档条目/脚本入口 → 原子能力编号 → DSH 分类与证据 → 本仓既定适配或待选方案 → 实现与审查结论 → 本阶段产物位置
```

报告未覆盖、证据不足和有意跳过项；为空时明确写“无”。每项来源、分类、证据和产物去向均可回查才可交付。
