# audit：审查并重建 pstack/README.md

唯一产物是简体中文的 `pstack/README.md` 移植审查记录。第 1～3 步只读取契约允许的取证材料，现有移植源码、生成树、旧 README 和其他分支说明留待各自规定的阶段。

## 1. 清点需求与模板

确认两个上游路径并记录提交。枚举并逐份读取 `<pstack>` 下全部 `*.md`、`*.mdc` 及文档形式的 agent/automation 模板与提示。按出现顺序登记“来源文档 + 章节/条目 + 原始要求”；重复需求先保留，清点完成后归并并保留全部来源。每份文档都有能力条目或“无可移植能力”标记，搜索命中不能替代全量清点。

完整读取 `<pstack>/docs/harness/claude-code.md`，登记其覆盖域、表格粒度、行为说明和平台排除基线，作为审查的组织参照；运行时指令留给文档分支。

完成标准：每份文档均有原子能力条目或“无可移植能力”标记，重复需求保留全部来源；模板覆盖域和排除基线逐项有记录。

## 2. 逐项取得 DSH 证据

按契约先执行平台排除，再将保留能力归入映射、标准模式或可选插件。调查 `<dsh>` 时：

- 从实际入口、工具/事件/服务声明、配置 schema、包导出、插件 manifest、默认启用状态和测试追踪行为，记录版本与准确插件 ID。
- 分开调查标准模式与显式开启的可选插件；实验性插件归入可选插件层。
- 比较目标行为、生命周期和关键语义，而非名称相似性。
- 按契约为第 2、3 层记录支持范围、缺口、场景、建议和证据。

完成标准：每项能力恰有排除结论或一个主层；第 2、3 层的每条支持与不支持的陈述均有可打开的 DSH 文件行链接，每个缺口均有场景与建议；证据不足项显式保留为未决。

## 3. 冻结并自审结论

建立能力追踪表，逐项回查文档清单和 DSH 原文，检查上游新增能力是否已由 DSH 覆盖、上游已移除行为是否仍误列在范围内。

完成标准：每项能力恰有一个去向，全部第 2、3 层结论和缺口经原文复核；插件内实现集合只含 DSH 仍不完整的行为；此时尚未读取现有实现或旧 README。

## 4. 重建 README

现在读取已存在的 `pstack/README.md` 以满足写前读取要求；旧文不提供产品事实。按本轮证据重写为**移植审查记录**，采用以下结构：

1. **审查基线**：文档目的、上游提交、DSH 版本、标准模式边界、清点范围与分类计数。
2. **能力映射审查**：按工具、子代理字段、模型、setup-pstack、路径等模板覆盖域组织；每行含能力 ID、上游期待、DSH 对应项或缺失、语义结论和双方证据。setup-pstack 记录行为差异与缺口。
3. **标准模式与可选插件覆盖**：分别标明完全或部分覆盖；每项含支持范围、缺口、场景、建议及 DSH 证据，可选插件另含准确 ID、实验性状态和启用条件。
4. **平台排除审查**：逐项记录上游完整能力、排除依据和证据。
5. **插件内实现范围**：仅列仍不完整且确需本插件提供的能力，保留原子能力编号、验收行为和实现建议状态；平台排除项及其局部步骤不进入此集合。
6. **实现建议选择**：存在多种合理实现方式的能力逐项列出候选、限制与取舍，标为“待选择”；证据只支持一种方案时标为“证据唯一”。用户选定后写为“已选择”，记录所选候选、关键边界与确认日期。
7. **文档追踪与未决证据**：每份上游文档都有去向，明确证据不足项及验证范围。

每项按“上游期待 / DSH 实际 / 审查结论 / 证据”陈述，必要证据随项保留；运行时引导与面向用户的操作说明留给 `dsh.md`。

完成标准：全部原子能力均有去向，每个第 2、3 层条目具备所需场景与证据；待实现集合不含映射、配置、平台排除项或 DSH 已有能力，实现建议状态均由本轮调查或用户确认产生。

## 5. 验证、报告并停止

重新打开全部证据，核对路径、行号和含义；回查文档来源去向，验证 README 相对链接可解析。报告上游提交、文档与能力计数、各分类计数、插件内实现项、未决证据和输出路径。

无法证实的关键能力保留醒目标记并在报告中列出。报告后结束本分支，等待用户显式调用 `implement`；存在“待选择”方案时，列出需在下次调用确认的能力编号与候选。
