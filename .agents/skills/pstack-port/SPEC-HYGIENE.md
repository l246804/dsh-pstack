# SPEC 自洁规则

`SPEC.md` 是用户锁定的基线，平时只追加。长期追加会让同一功能散在多处、术语分裂、完成标准重复，整份文件读起来不再连贯。**自洁**是在用户明确要求时做一次整文件整理，恢复连贯，不改功能。

## 何时自洁

- 用户明确要求「SPEC 自洁」时执行；没有要求就只追加。
- 用户没要求时，发现同类要求散在三处以上、一个概念出现两种说法、或同一完成标准重复，在报告里提议自洁，不自行执行。

## 不变式

- **功能完整性**：每个场景的触发、前置状态、期望行为、状态与文件变化、下一步、明确不做、验收证据都保留。
- **正确性**：要求含义、编号、状态值与路径不变；不新增用户未描述的场景（SPEC §0 规则 5）。
- **编号不复用**：旧编号继续指向同一要求。

## 冲突处理

同一功能存在互相冲突的多种说法时，先停下，不改文件。报告四件事：冲突位置（编号与行号）、说法 A、说法 B、两者差异与建议改法。等用户确认后再动。没有冲突才进入整理。

## 自洁流程

1. **盘点**：通读全文，列出编号、每条的意图与所属阶段，标出重复、散落、过期和术语不一致。
2. **分类**：每条差异归为「纯表达」或「语义冲突」。纯表达直接改；语义冲突按上一节报告。
3. **整理**：按 `/writing-for-agents` 的信息层级与 pruning 规则重排与改写：合并重复、统一术语、把定义与规则放回同一标题、删无效句、修正指针与完成标准。保持场景字段顺序与既有编号。
4. **核对**：用盘点表逐条确认原要求仍可定位；对照 SPEC §0 的只追加与范围规则，确认没有引入新场景。
5. **报告**：给出对照表（旧编号或位置 → 新位置 → 处理：保留、合并、改写），列出提议与用户确认的冲突结论，报告整理前后的条目数。

## 明确不做

- 不新增、删除或弱化任何功能要求；不改变验收证据的含义。
- 不自行消解冲突；不把 agent 推断写进 SPEC。
- 不在自洁时改本文件；需要改本文件时按同样流程由用户确认。
